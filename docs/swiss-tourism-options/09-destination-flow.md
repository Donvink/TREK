# 09｜目的地游客分流与地方体验匹配

> 方向：目的地机构采购、多方参与｜版本：v0.1｜日期：2026-10-06
>
> 这是合作与测量门槛较高的方向。六周目标是有限试点，不承诺完成公共采购。共同规则见 [00](00-common-foundation.md)。

## 1. 定位与问题

帮助目的地管理机构将游客匹配到条件合适、仍有接待能力的地点与体验，通过住宿入口提供建议，并测量实际到访和商家结果。

首个客户需有明确预算负责人和分发渠道，例如一个地区的目的地管理机构、酒店联盟或合作项目。首期只覆盖 5–10 家体验方与两三家分发酒店。

待验证假设：存在需要解决的游客集中问题；替代体验有需求与容量；机构愿意采购；商家愿意提供状态；结果能够合法可靠地测量。

## 2. 发散方向

| 延伸 | 任务 | 试验 |
| --- | --- | --- |
| 同日空间分流 | 热门点繁忙时推荐合适替代 | 先用运营方确认状态，不伪造实时人数 |
| 淡季体验 | 推广季节适宜的地方活动 | 分开比较淡季需求与曝光 |
| 延长停留 | 给住客第二天不同体验 | 测实际新增活动，不只收藏 |
| 小商家曝光 | 匹配兴趣与经营时间 | 记录曝光、到访与可归因收入 |
| 无车地区玩法 | 引导可公共交通到达地点 | 同时核验到达与返回能力 |
| 容量预约建议 | 防止集中推荐造成新拥挤 | 需要真实预约或容量来源 |
| 可持续体验导览 | 解释已核验的服务特点 | 不自行授予认证，不用标签代替效果 |

瑞士已有 Swisstainable 计划，可以作为合作背景与竞品研究来源，但不意味着本产品被认证或已有合作。[官方计划](https://www.myswitzerland.com/en-us/planning/about-switzerland/sustainability/)

MVP 选择“人工容量状态 + 酒店分发 + 兴趣匹配 + 到访反馈”，不建立预测全地区拥挤的模型。

## 3. 产品设计

游客：从酒店入口填时间与兴趣 → 查看可达体验 → 了解匹配原因及商业关系 → 保存路线或向运营方预订 → 自愿提供采用反馈。

商家：提交开放时间、可接待时段和状态 → 机构核验 → 到期更新。机构：查看内容覆盖、来源质量、分发和聚合效果。

页面：游客推荐、商家状态提交、机构审核、聚合仪表盘、实验报告。人工“可接待”必须显示提交时间与有效期，不等同实时客流。

不公开商家的未经授权营收，不向机构展示游客完整位置轨迹。首版通过自愿反馈或合作商家确认到访，不持续定位。

## 4. 技术设计

复用 TREK 地图、行程、公共入口、天气、交通和分享。新增 `DestinationFlowModule`：内容审核、容量状态、曝光分配、实验和聚合。

| 对象 | 内容 |
| --- | --- |
| DestinationProgram | 地区、客户、合作规则与时间范围 |
| ExperiencePartner | 商家、地点、兴趣、授权状态 |
| CapacityStatement | 时间段、容量等级、来源、有效期 |
| RecommendationExposure | 匿名会话、候选与展示、实验组 |
| VisitEvidence | 自愿反馈或授权合作确认、证据类型 |
| ExperimentAssignment | 随机单位、规则版本、开始与结束 |
| AggregateOutcome | 样本、漏斗、到访与不确定性 |

接口：`POST /api/destination/recommendations`、`POST /api/destination/partners/:id/status`、`POST /api/destination/visits`、`GET /api/destination/admin/outcomes`。

### 4.1 推荐逻辑

先满足时间、交通、营业与游客偏好；容量作为约束或排序因素。已知无容量的项目排除，容量未知不伪装为低客流。

加上曝光上限与多样性，防止所有用户同时收到同一替代。曝光并不等于实际预约，不能把每次推荐当作消耗一个真实名额。

商家商业关系与自然适配分开显示。轮换曝光不能牺牲游客硬约束；保留规则版本用于解释与审计。

### 4.2 实验设计

小样本首期只描述采用与到访，不声称因果。条件允许时，先确定随机单位：同酒店会话随机分为常规建议与匹配建议，双方都满足基本约束。

先定义主要结果为“自愿或授权证据支持的实际到访”，收藏为次要指标。报告分母、证据缺失、取消、时间与天气差异。

游客与商家可能互相影响，统计独立性不一定成立。真实容量与流量外溢也会改变结果；需要在扩展时咨询实验方法，不凭几次点击得出“减少拥挤”。

### 4.3 隔离与运行

首期单地区独立实例，各角色检查机构与商家归属。容量过期降级，商家状态不能未经审核发布到高影响推荐。

测试营业时间、容量过期、曝光上限、合作标记、越权修改、实验组一致性和到访去重。AI 只解释，不预测没有训练数据的客流。

### OJP 适配器接入（新增任务）

在现有 `server/src/nest/transit/` 中增加 OJP 2.0 provider，服务端转换为现有交通协议，复用前端接口。排除交通不可达或不满足返回约束的地方体验。

第 1 周验证权限与样本，第 3 周实现 provider 与配置，第 4 周联动业务约束及失败降级。尚未实现；完整鉴权、字段、缓存与验收见 [共用 OJP 设计](00-common-foundation.md)。

## 5. 六周计划

| 周 | 工作 | 交付与门槛 |
| --- | --- | --- |
| 1 | 访谈机构、酒店与商家，找预算与数据负责人 | 一地区负责人、分发承诺和测量许可；否则停止机构平台 |
| 2 | 收集 5–10 家体验内容、状态与测量流程 | 核验字段、人工推荐试验、合作记录 |
| 3 | 角色与审核、状态模型、推荐规则 | 样本结果与权限测试 |
| 4 | 入口、容量新鲜度、聚合事件与到访反馈 | 可运行试点、漏斗定义 |
| 5 | 酒店分发、商家更新、有限实验 | 实际曝光和证据支持到访；不承诺统计显著 |
| 6 | 测量限制、采购与成本复盘、参赛材料 | 地区案例、预算意向与扩展前提 |

若机构审批超时，可执行商家联盟的小试验，但明确其代表性与客户不同。没有测量入口不继续做复杂预测。

## 6. 收费实验

| 模式 | 假设价格 | 范围 | 判断 |
| --- | --- | --- | --- |
| 有限试点服务 | CHF 1,000–3,000／项目 | 六周、限定商家与分发点 | 预算负责人愿否实际采购 |
| 持续地区服务 | CHF 500–1,500／月 | 限定维护与报告额度 | 状态维护、支持与销售成本 |
| 商家联盟版 | CHF 50–100／商家每月 | 透明内容与使用报告 | 是否愿意参与且不会扭曲推荐 |

价格不是已研究的机构采购水平。首轮以工作范围报价，区分软件订阅与咨询服务。避免把免费研究合作计作收入。

佣金留作后续，先有合法归因、合同与结算机制。不要承诺不可控制的到访量或收入。

## 7. 指标与决策

测量合作方更新率、有效状态比例、推荐展示、方案保存、证据支持到访、各商家分布、用户满意度与实施工时。

初期目标：5 家活跃体验方、2 家真实分发点、50 个推荐会话和至少 15 份采用反馈。只是试点规模目标，不足以证明游客分流。

如果没有预算负责人、更新积极性或结果测量路径，不投入目的地平台。若游客不接受替代，先检查体验与需求匹配，不用强制分流提高指标。

## 8. 参赛准备

若核心是游客分布与地方影响，可考虑 Social & Environmental Impact；否则 Consumer Solutions。必须根据实际价值选一个类别。

- 创新：游客约束、商家状态、透明曝光与结果测量结合。
- 团队：机构合作、数据治理、实验与产品能力。
- 技术：过期状态、曝光约束、审核与测量设计。
- 市场：具体地区采购流程和商家参与，而非全国旅游规模推导。
- 影响：实际到访分布与商家结果；不声称仅推荐就减排或减拥挤。
- 商业：项目预算、持续合同、内容与报告成本。

演示：商家更新容量 → 审核 → 推荐变化 → 过期后降级 → 显示到访证据与缺失比例。提供测量设计和失败结果，可信度优于过度宣传。

## 9. 下一步

优先确认机构负责人、可采购预算、数据与测量许可。Swisstainable 相关信息与商家资质需按官方当前定义核验。
