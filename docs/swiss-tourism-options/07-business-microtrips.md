# 07｜商务与会议短时旅行

> 方向：在固定日程之间安排当地体验｜版本：v0.1｜日期：2026-10-06
>
> 所有数量、收费与效果均是实验假设。共同约束见 [00](00-common-foundation.md)。

## 1. 定位与首个客群

为会议参与者或商务旅客安排半小时至半天的当地体验，围绕下一项会议、酒店或机场返回时间规划。

首个渠道是一个会议主办方或一家商务酒店，覆盖一个会场周边。客群可先选会后仍有两三小时的参与者，避免同时覆盖机场中转、跨境签证和接待团队。

关键假设：参与者愿意离开会场或酒店；有足够空闲窗口；主办方认为当地体验能改善活动服务，并有采购预算。

## 2. 发散方向

| 延伸 | 场景 | 验证 |
| --- | --- | --- |
| 会后两小时 | 会议结束与晚餐之间 | 真实采用和返回时间 |
| 机场前半日 | 退房后等航班 | 用户指定最晚到机场时间，验证交通 |
| 陪同家属路线 | 主参会人日程固定 | 访谈家庭，不默认需要相同活动 |
| 会场午休体验 | 午休只有四十五分钟 | 测返回可靠性与实际兴趣 |
| 社交体验组 | 少量参会者一起参加 | 自愿加入、隐私与组织责任 |
| 公司差旅福利 | 企业为员工提供目的地内容 | HR／差旅负责人预算 |
| 目的地会议合作 | 同城市多个会场共享内容 | 采购成立后再做平台化 |

MVP 做“会后两小时 + 必须按时返回”，机场分支可作受限样例，不推荐紧张窗口离开机场。

## 3. 产品流程

主办方提供活动码 → 参与者选择空闲时间 → 设定下一地点和最晚到达 → 选择兴趣、步行与行李条件 → 比较方案 → 保存 → 查看返程提醒。

页面：活动欢迎页、时间输入、方案比较、行程与倒计时、返回交通。固定时间显示实际日期和当地时区，不能仅显示“两小时”。

用户设置缓冲，系统给默认示例但不称为机场官方要求。航班分支以用户明确的“最晚到机场时间”为约束；不依据飞行时间自动保证不会误机。

首版 10–15 条会场周边路线、1–2 个活动入口，英文与当地语言。行李寄存需来源与当前开放核验；未知条件下不安排依赖寄存的路线。

## 4. 技术设计

已有行程、日历、地图、交通、天气和分享可复用。新增 `MicrotripModule`，核心是固定时间边界与受限推荐。

| 对象 | 内容 |
| --- | --- |
| EventProfile | 会场、时间范围、品牌与公开内容 |
| AvailabilityWindow | 出发、必须到达、缓冲和用户时区 |
| MicrotripTemplate | 最小体验时长、返回点与可缩短分支 |
| ReturnConstraint | 目标地点、截止与关键交通段 |
| LogisticsObservation | 行李寄存、入口、排队等核验状态 |

接口：`GET /api/microtrips/events/:slug`、`POST /api/microtrips/recommendations`、`POST /api/microtrips/plans`、`POST /api/microtrips/plans/:id/recheck`。

### 4.1 算法

从返回截止反推：交通时长与缓冲 → 最晚离开活动点 → 可用体验时长 → 筛选模板。再验证从起点到活动点的交通与开放时间。

硬条件包含返回、活动最小时间、步行上限；排队等未知信息采用明确保守假设。没有方案时推荐留在附近或缩小活动，不强行满足用户想去的地点。

可缩短分支需要明确触发点。返回连接失效后重新检查，不仅减少剩余时间标签。

### 4.2 数据与权限

主办方只看到聚合使用，不看到个人日历。首版手动输入空闲窗口，不接入企业完整日历或差旅订单。机构试点实例隔离，访客私有会话单独检查。

天气与交通失败时保留快照，但停止展示已验证返回。需要后台提醒时必须有通知权限，不能依赖 PWA 一定推送成功。

测试会议跨日、时区与夏令时、短窗口、交通延误、寄存关闭、用户更改截止和通知失败。

### OJP 适配器接入（新增任务）

在现有 `server/src/nest/transit/` 中增加 OJP 2.0 provider，服务端转换为现有交通协议，复用前端接口。结合到达截止与用户缓冲，验证会场或酒店返回连接。

第 1 周验证权限与样本，第 3 周实现 provider 与配置，第 4 周联动业务约束及失败降级。尚未实现；完整鉴权、字段、缓存与验收见 [共用 OJP 设计](00-common-foundation.md)。

## 5. 六周计划

| 周 | 工作 | 交付与判断 |
| --- | --- | --- |
| 1 | 访谈 3 个主办方、10 位旅客，锁定活动日期 | 实际分发承诺、采购流程；无活动则商务酒店替代 |
| 2 | 核验会场周边路线，人工推荐 | 10 条模板、返回条件、真实空闲窗口 |
| 3 | 活动入口、时间窗、反向求解 | 返回约束样本与页面 |
| 4 | 交通重检、短版、快照与统计 | 手机全流程和故障测试 |
| 5 | 活动或酒店试点、真实报价 | 使用与返回反馈、运营工时 |
| 6 | 主办方采购复盘与参赛材料 | 演示、付款／意向区分、活动周期风险 |

活动时点不匹配时六周内可完成产品与小试验，但不能声称已经跑完大会。需要在第一周就排定测试机会。

## 6. 收费实验

| 模式 | 假设价格 | 权益 | 验证 |
| --- | --- | --- | --- |
| 单活动服务 | CHF 300–800 | 一会场、限定模板、分发与聚合报告 | 主办方实际采购 |
| 商务酒店订阅 | CHF 149–299／月 | 酒店出发的短时路线 | 分发、采用和采购 |
| 游客人工方案 | CHF 9–19 | 一次时间窗推荐与核验 | 是否有直接付费需求 |

不同模式是备选，不在同一批用户重复收费。单活动价格需记录准备、内容与现场支持工时；免费合作也记录成本，避免低估实施。

## 7. 验证指标

记录空闲窗口长度、无结果原因、保存、实际采用、按用户设定时间返回与主办方反馈。访问二维码不等于离开会场体验。

建议首批至少 30 个有效会话、10 个实际采用反馈，争取一笔机构付费。任何已知违反硬返回条件的推荐先阻断，再复盘。

如果窗口普遍太短或旅客更想休息，不强推景点，可转为附近餐饮／散步内容。若主办方只买品牌展示，重新判断是否存在可扩展产品。

## 8. 参赛准备

拟选 Consumer Solutions，按机构采购表述不自动改变类别。

- 创新：固定时间边界、物流与可缩短体验的联合推荐。
- 团队：会议渠道、当地内容与时间约束技术。
- 产品：同一地点不同时间窗的可行性变化。
- 市场：活动频率、渠道预算、个人使用场景。
- 影响：商务客的当地体验与商家机会，需要实际采用。
- 商业：单活动支付、获客与内容复用成本。

演示：两小时窗口推荐 → 缩短至四十五分钟 → 排除远程活动 → 已知返程变化 → 选择短版并显示来源。与人工会场手册和现有目的地推荐做比较。

## 9. 下一步

确定可接触会场、测试活动日期与最晚返回定义。交通与地图来源见共同文档；涉及机场要求时以具体机场与用户情况核验。
