# 06｜酒店数字礼宾

> 方向：住宿机构采购、住客使用｜版本：v0.1｜日期：2026-10-06
>
> 本文件是独立方向设计；扩展细节见 [原酒店主方案](../swiss-tourism-venture-design.md)。共同规则见 [00](00-common-foundation.md)。

## 1. 定位与假设

住客从酒店入口获得多语言当地建议，前台维护一批可靠内容，酒店知道推荐的使用情况。核心付费价值是减少重复咨询和改善服务，尚需证据。

首个客户优先独立酒店或小型酒店集团。先选一个地区的两三家，不以大型 PMS 集成为前提。

访谈确认酒店当前用什么、咨询频率、维护责任、谁批准采购与谁能实际分发。已有礼宾、住客服务和酒店软件必须纳入竞品分析。

## 2. 发散方向

| 延伸 | 产品形态 | 收费与验证 |
| --- | --- | --- |
| 前台问答资料库 | 经核验的多语言地点与路线 | 看咨询时间，不只测聊天次数 |
| 扫码个性化行程 | 根据住客时间和体力推荐 | 酒店分发与采用率 |
| 天气备选礼宾 | 明天活动变化时给替代 | 实际建议采用，结合 02 |
| 家庭或多代路线 | 酒店特定客群内容 | 结合 04／05，分别验证 |
| Guest Card 导览 | 解释当地住宿权益 | 从酒店核验规则，不自行承诺资格 |
| 地方体验入口 | 酒店合作商家的适配推荐 | 标记商业关系，测真实转化 |
| 酒店集团内容平台 | 共用地区内容、独立品牌 | 采购成立后再做共享租户 |

MVP 选择扫码行程、酒店内容后台和聚合统计，动态调整可以只加入简单雨天备选。

## 3. 产品设计

住客：扫码 → 酒店欢迎页 → 少量偏好 → 比较路线 → 保存私有行程 → 联系前台／反馈。

酒店：开通 → 核对地址与路线 → 管理内容 → 获取二维码 → 分发 → 查看使用与待核验项。

页面：欢迎页、偏好表、推荐与行程、员工内容页、管理员报告。明确酒店推荐、平台推荐和付费商家三类标识。

首版每酒店可配置品牌、联系方式和推荐模板。内容包覆盖 20–30 个核验地点、10–15 条路线即可；实际范围随维护能力调整。

首版不自动读取 PMS、房间或预订身份；酒店公共码不能读到游客明细。前台需要协助时由游客主动分享。

## 4. 技术设计

已有 TREK 的行程、地图、公开模板、权限、实时同步与离线可复用。新增 `HotelConciergeModule` 与匿名私有身份。

| 对象 | 内容 |
| --- | --- |
| HotelProfile | 品牌、位置、时区、公开配置 |
| StaffRole | 内容编辑、前台、管理员 |
| GuestSession | 私有身份、到期、恢复和删除 |
| HotelContentAssignment | 酒店与内容包版本 |
| BenefitRule | 当地权益、来源、范围与有效期 |
| GuestPlan | 会话归属、行程、版本 |
| HotelMetricAggregate | 事件计数与统计窗口 |

接口：`GET /api/concierge/hotel`、`POST /api/concierge/sessions`、`POST /api/concierge/recommendations`、`POST /api/concierge/plans`、`GET /api/concierge/admin/metrics`。

### 4.1 部署与身份

两三家试点采用独立应用实例、数据库、文件与备份。每实例内部继续做游客私有权限。规模化共享租户是另一个项目，不能只添加酒店编号。

先验证匿名主体能否安全接入 TREK 行程；不复用一个普通账户给全部游客。访客守卫默认拒绝通用用户与管理员接口。

### 4.2 内容与推荐

共享公开核验内容可以分发为带版本的内容包；酒店私有配置不混入包。规则先过滤时间、营业、体力与未知条件，再排序。

后台展示每条内容的核验人、有效期与到期提醒。AI 可解释与翻译，但不能生成未核实事实。

### 4.3 测试与运行

重点测试公共码不越权、员工权限、内容版本、跨实例文件与缓存隔离、匿名恢复、删除、统计聚合和供应商故障。

上线配置 HTTPS、持久化存储、备份恢复和供应商额度。页内使用统计不暴露原行程或身份给酒店。

### OJP 适配器接入（新增任务）

在现有 `server/src/nest/transit/` 中增加 OJP 2.0 provider，服务端转换为现有交通协议，复用前端接口。验证从酒店到景点、景点之间及返回酒店的连接。

第 1 周验证权限与样本，第 3 周实现 provider 与配置，第 4 周联动业务约束及失败降级。尚未实现；完整鉴权、字段、缓存与验收见 [共用 OJP 设计](00-common-foundation.md)。

## 5. 六周计划

| 周 | 工作 | 交付与门槛 |
| --- | --- | --- |
| 1 | 访谈 8–12 家酒店，选择地区 | 两三家有分发承诺，采购与维护责任清楚 |
| 2 | 人工礼宾和内容核验 | 10 次推荐反馈、首批模板、入口文案 |
| 3 | 独立实例、欢迎页、身份与私有行程 | 手机流程、隔离与归属测试 |
| 4 | 推荐、地图、酒店后台和反馈 | 内容更新与故障降级可用 |
| 5 | 真实分发、聚合统计、订阅报价 | 入口触达与采用数据、前台记录 |
| 6 | 采购复盘、成本、演示与申请 | 真实付款／意向区分、案例报告 |

没有实际住客分发不算完成试点。低扫码先检查入口，而非立即升级算法。

## 6. 收费实验

| 模式 | 假设价格 | 权益 | 检验 |
| --- | --- | --- | --- |
| 基础订阅 | CHF 99／149／199 月费轮换讨论 | 一个地区、品牌和限定活跃会话 | 采购理由与真实支付 |
| 内容与服务版 | CHF 299–499／月 | 更多核验内容和支持额度 | 人工工时与贡献率 |
| 一次上线费 | 根据实际工时报价 | 品牌、配置与员工培训 | 是否帮助覆盖获客与实施成本 |

试用后按预先约定报价，不把长期免费试用当作付费客户。费用与额度透明，不同时向住客收取未说明的基础服务费。

主要成本是内容和支持，记录每家每月工时。若售后比调用费高，优先简化服务范围。

## 7. 指标与停止

记录可测触达、扫码、表单完成、方案保存、实际采用反馈、前台咨询用时、报价与付款。

初始目标：三家完整试点、50 个有效推荐会话，至少两家愿按明确条件延续，争取一笔真实订阅。付费未实现时如实说明销售周期，不用口头喜欢替代。

如果游客使用但酒店不愿付款，检查酒店结果是否可测，或尝试体验渠道收入；如果酒店不分发，优先解决工作人员流程。

## 8. 参赛准备

拟选 Consumer Solutions；核心是住客体验与明确酒店商业入口。

- 创新：酒店入口、核验内容、个人约束及动态备选的实际结合。
- 团队：销售、内容运营、隐私与软件负责人。
- 产品：真实酒店手机流程和隔离验证。
- 市场：酒店采购、现有礼宾软件与前台替代方式。
- 影响：可衡量服务与当地体验采用，不预设减排。
- 商业：分发、付款、续用与内容支持贡献。

演示：酒店扫码 → 私有推荐 → 员工更新一项内容 → 新推荐反映变化 → 酒店报告只见聚合数据。提供前台时间样本与采购证据。
