# 十方向共用改进机会：从交通查询到可执行旅行服务

> 日期：2026-10-06｜状态：发散设计，未实现、未验证
>
> 本文是对现有十个方向的横向改进，不新增第十一个创业方向。OJP 适配器已纳入技术路线，接入设计见 [共同基础](00-common-foundation.md)。

## 1. 产品改进机会

### 1.1 从“去哪”变成“这些条件下去哪”

用户输入自然语言：从酒店出发、只有四小时、最晚六点回来、预算范围、推车、最长连续步行。系统先转换成可编辑约束，用户确认后再求解。

技术：结构化输入、规则校验、模板候选、OJP 交通验证；AI 解释约束但不直接宣布方案可行。

适用：01、04、05、06、07。先测约束理解准确率、候选采用率和错误推荐，而非对话长度。

### 1.2 时间与预算的可达地图

用户拖动“可用时间”和“愿意花费”，看到在往返交通、停留和步行要求下可以考虑的地点。候选圈不能仅按直线距离画。

技术：先在有限地点库中批量验证连接与返回，缓存重复查询。没有完整价格就显示费用未知，避免把可达圈误写成预算已满足。

适用：01、03、06、07。首版只显示可行候选点，不急于生成精确连续等时线。

### 1.3 换乘宽松程度与全日负担

同一旅程可比较最快、少换乘、步行少、余量更多的方案。对家庭和老人，少一段紧张换乘可能比少十分钟更有价值。

技术：计划换乘余量、可用预测时间、总步行和最大连续步行分别呈现。先做可解释指标；没有历史校准数据时，不输出“错过换乘概率 12%”之类数字。

适用：02、04、05、08、10。测用户选择与真实执行问题。

### 1.4 固定项目与可调项目

用户把午餐、预约、已购票和会面标成不可移动。调整时保留这些项目，解释冲突，并允许用户主动解除限制。

技术：约束优先级、预约锁、版本快照和原子确认；实际供应商订单保持独立状态。

适用：02、06、07。首版不要自动变更外部预订。

### 1.5 每套方案都有备选和短版

给用户一套主计划、雨天备选和体力下降后的短版。备选需要实际交通与营业验证，不能只替换景点名字。

技术：活动类别匹配、局部时间窗口求解、退出节点与返回连接。备选只在用户选择后更新正式计划。

适用：02、04、05、06、08。测实际缩短与替换采用。

### 1.6 按地点与时段匹配天气

观景、步行和室内活动分别匹配其计划地点与时段，尽量避免用酒店所在城市的全天图标代表整个旅程。

技术：地点预报与时间窗、来源更新时间、明确的活动规则。山地观景可以评估已获取的云、降水等参数，但不保证能见度或安全。

MeteoSwiss 当地预报数据包含邮政编码、山地兴趣点及站点等位置；短临预报也是可研究来源，具体覆盖、参数和处理成本需验证。[当地预报](https://opendatadocs.meteoswiss.ch/e-forecast-data/e4-local-forecast-data)、[短临预报](https://opendatadocs.meteoswiss.ch/e-forecast-data/e1-short-term-forecast-data)

适用：01、02、06、08。先做规则，不训练天气预测模型。

### 1.7 已有票券和住宿权益

收集用户已有票券，让建议显示覆盖、额外费用与待确认项；酒店可解释其核验的 Guest Card 权益。

技术：票券规则版本、覆盖矩阵与独立报价任务。OJP 路线接入不能直接推出所有价格。

适用：01、03、06、08。先做少量权益，不承诺全球最优组合。

### 1.8 最后一段路与现场细节

交通站到入口可能有坡度、台阶、行李负担或排队。加入入口位置、接驳步行、休息和寄存信息，让推荐落到真实执行。

技术：设施观察、三态数据、有效期和现场核验。未知台阶不等于无台阶；推车友好不等于所有轮椅用户可达。

适用：04、05、06、07、08。这是人工内容工作的重点。

### 1.9 逐项可核验的行程说明

每段活动显示为什么适合、时间依据、信息来源、更新时间和未知项。用户可以点开，而不是接受一个笼统“推荐置信度”。

技术：事实与文案分离、来源绑定、报价快照、规则版本。可验证与解释性是产品能力，不能声称整条行程有官方安全认证。

适用全部方向。测关键事实错误率、来源覆盖和用户理解。

### 1.10 轻量导入与确认

从用户文字、截图或转发内容提取已有活动和约束，降低填写成本；提取后逐项确认。

技术：结构化解析、实体匹配、日期与时区校验、敏感信息清理。现有预订解析可复用，但不能把未经确认的文本直接变为硬事实。

适用：02、03、05、07、10。先支持手动粘贴，后续再做图片与文档输入；私有账户接入另行授权。

### 1.11 旅行过程中只给当前需要的信息

在出发前显示交通与核验；到达后显示入口、活动与下一段；有变化时才突出备选。避免整天展示几十条提醒。

技术：行程时间驱动的状态机，用户主动确认进度；首版不需持续定位。离线仍显示原计划与快照时间。

适用：02、04、05、06、07、08。测提醒关闭、实际采用和遗漏。

### 1.12 朋友或家人分别填写私有偏好

成员填自己的预算、时间和体力；组内显示共同可行方案与聚合冲突，不曝光每个人的理由。

技术：私有成员偏好、共享摘要、公平目标、投票版本和撤回权限。

适用：04、05、10。只做小组，先解决参与者不愿填表的问题。

### 1.13 酒店工作人员辅助与知识传承

前台用一句话生成草案，查看依据、编辑并发给住客；员工记录哪些问题需要核验，其他班次能复用。

技术：员工审核、酒店内容版本、反馈入库、来源状态与有限审计。私人住客资料不自动成为酒店知识库。

适用：06，并可连接 02、04、05。可与 Work, Reimagined 主题形成关联，但需真实员工流程与测量。[Spotlight 官方主题](https://www.venture.ch/copy-of-spotlight-award-1)

### 1.14 商家状态、到期提醒与反馈闭环

酒店或商家报告临时关闭、时段容量、设施问题。系统将其变成待审核信息，影响新推荐，并提醒过期复核。

技术：贡献者权限、审核队列、有效期与相关行程的影响检查。用户反馈不未经核验直接覆盖事实。

适用：06、09。测更新率、核验时间和真实到访证据。

### 1.15 可拆分的接口与插件能力

同一“解释候选、检查可行性、建议替代”能力可用于酒店页面、机构工具或经授权的 AI 助手。

技术：统一领域接口、明确 scopes、调用预算、幂等写入与审计。MCP 可作为后续入口，规则与权限留在领域层；不能先开放所有管理工具。

适用：02、03、06、09、10。先证明网页流程价值，再扩展集成，避免过早平台化。

### 1.16 把用户拒绝变成可行动的反馈

选择“不想去”时提供少量原因：太远、太贵、走太多、去过、信息不清。下一次推荐尊重历史，内容编辑知道什么需要改。

技术：自愿偏好记忆、数据删除、规则调优和匿名聚合；不需要跨酒店追踪身份。

适用：01、04、05、06、10。测再次采用，避免只优化点击。

## 2. 技术体系的改进

1. **规则与生成分开。** 由领域规则产生可行候选，LLM 解释和理解输入。继承创始人的结构化 LLM、故障隔离与生产交付经验。
2. **供应商统一协议。** OJP、现有交通与天气来源在服务端适配；缓存、来源和异常可追溯。
3. **每阶段可观察。** 记录无候选究竟来自时间、交通、内容还是供应商；统计推荐成本与人工支持，不记录无必要个人原话。
4. **固定样本评估。** 建立跨日、夏令时、锁定预约、未知价格、推车和成员冲突等边界场景，避免只展示成功案例。
5. **失败保持语义。** 错误、无路线和未知分开；原计划保留，不把失败转成正常状态。
6. **来源新鲜度分层。** 营业、天气、交通和设施有不同更新周期；动态信息采用短缓存，静态资料经核验后复用。

瑞士交通平台说明实时数据按供应商提交质量提供，因此实时状态不是无条件完整或正确。[实时数据说明](https://opentransportdata.swiss/en/cookbook/realtime-prediction-cookbook/)

## 3. 适合首版的组合

| 组合 | 首个付费方 | 首版重点 | 延后 |
| --- | --- | --- | --- |
| 酒店 + 约束 + OJP + 核验说明 | 酒店 | 可执行建议和工作人员审核 | PMS、全国内容、自动购票 |
| 周末 + 时间可达 + 票券信息 | 居民或雇主 | 重复使用和实际出行 | 全票种实时价格、社交平台 |
| 家庭／父母 + 现场设施 + 短版 | 家庭或住宿机构 | 体力与节奏真实满足 | 普遍无障碍、医疗相关判断 |
| 动态行程 + 锁定项目 + 状态快照 | 游客或机构 | 变化后仍可执行 | 自动改订和高风险活动 |

对当前独立创始人，建议先选一个组合验证，不同时叠加全部机会。工程实力可以提高可靠性，旅游内容、渠道与采购仍需实际访谈。

## 4. 建议实施顺序

第一层：结构化约束、有限核验模板、OJP 适配、时间与返回验证、来源与未知状态。

第二层：备选与短版、锁定项目、用户确认、酒店员工编辑与真实反馈。

第三层：票券范围扩展、成员求解、MCP 集成、学习排序和机构效果测量。

优先验证“用户是否采用、能否执行、谁支付”。观景质量、实时容量、无障碍和复杂票价需要专门数据，不作为附带承诺。

## 5. 申请材料如何体现

Innovation 写一个真实核心机制，例如“在固定预约、体力和返回约束下，生成基于可核验信息的替代计划”，不要把十六项列为均已拥有的创新。

Technology 写现有 TREK 基础、计划中的 OJP provider、规则与事实协议、验证及失败处理。Team 使用真实生产 AI 和 SaaS 经历，Market 保留未验证状态。

Work, Reimagined 如选择酒店路线，应证明知识复用、前台辅助和员工能力支持，同时测新增核验负担。拥有 AI 或 MCP 接口本身不证明工作主题价值。
