# 共同约束、技术底座与参赛规则

> 十个独立方案共同引用本文件。所有价格和目标是实验参数，外部资料核对日期为 2026-10-06。

## 1. 现有技术与新增能力的边界

TREK 是 TypeScript 全栈应用：React 前端、NestJS 后端、SQLite、WebSocket，前后端共享 Zod 协议。已有行程、每日安排、地图、预订、预算、协作、分享和离线能力。

可参考的真实路径：

| 能力 | 路径 | 边界 |
| --- | --- | --- |
| 行程 | `server/src/nest/trips/`、`server/src/nest/days/` | 不是新推荐引擎 |
| 交通 | `server/src/nest/transit/` | 当前默认 Transitous，并非已经集成 OJP |
| 天气 | `server/src/nest/weather/` | 当前使用 Open-Meteo，并非已经集成 MeteoSwiss |
| 预算 | `server/src/nest/budget/` | 费用记录不等于实时票价查询 |
| 协作 | `server/src/nest/collab/` | 投票聊天不等于多人约束求解 |
| 分享 | `server/src/nest/share/` | 公开只读分享不等于匿名私有会话 |
| 地图与路线 | `server/src/nest/maps/`、`server/src/nest/roadtrip/` | 普通路线能力不等于可靠户外路线或无障碍认证 |
| 休假与日历 | `server/src/nest/vacay/`、`server/src/nest/calendar/` | 能力存在，是否适合新流程要另行检查 |
| 离线 | `client/src/sync/` | 快照不能代表当前实时状态 |
| 共享协议 | `shared/src/` | 新字段和 API 需要新增协议 |

初期坚持一个 NestJS 应用内的清晰领域模块，不默认拆成微服务；已有 SQLite 可用于单节点试点。涉及数据库迁移、用户身份和公开路由，需要先检查现有全局守卫及业务假设。

## 2. 新模块通用结构

每个方向至少分清四类职责：用户流程与接口、领域规则、数据供应商适配、内容与运营管理。AI 是可替换的解释或输入辅助组件，事实与约束由结构化数据决定。

新模块名、对象和接口均是提案，未开始实现。请求和响应放入 `shared/` 校验，业务规则放在领域服务中，供应商响应先转换再进入业务。

记录关键来源的 `source_url`、`retrieved_at`、`verified_at`、`valid_until`、`status`。信息状态至少有已确认、待核验、过期、未知，不用空字符串掩盖未知。

### 2.1 新增任务：在现有交通模块中增加 OJP 适配器

状态：已纳入产品与技术路线，尚未实现或取得 API Key。目标是让推荐直接验证瑞士公共交通连接、换乘和到达／返回时间。

计划在 `server/src/nest/transit/` 增加 `ojp-transit.provider.ts`，由现有 `TransitService` 分发调用，并在 `TransitModule` 注册。前端仍使用既有 `/api/transit/geocode` 与 `/api/transit/plan`；OJP 的 XML 和认证仅由服务端处理。

| 改造位置 | 计划 |
| --- | --- |
| `transit-provider.ts` 与共享 `TransitProvider` 定义 | 新增 `ojp` 供应商选项及配置校验 |
| 新增 OJP provider | 实现地点查询与路线规划，转换为 `TransitPlace`、`TransitItinerary`、`TransitLeg` |
| `transit.service.ts`、`transit.module.ts` | 按供应商选择调用，明确实际响应来源 |
| 配置与管理页面 | 服务端保存和掩码显示 API Key，允许选择 OJP；密钥不进入浏览器 |
| 前端供应商标识与缓存 | 标识 OJP／降级来源；缓存包含供应商、参数与获取时间 |
| 行程约束模块 | 校验关键换乘、步行接驳及最晚返回，不把单段查询当完整行程可行性 |

接入入口为 `POST https://api.opentransportdata.swiss/ojp20`，使用 API Manager 申请的密钥和 XML 请求。第一步基于官方 OJP 2.0 文档与样本验证实际支持的服务和过滤条件，再实现映射。[官方说明](https://opentransportdata.swiss/en/cookbook/open-journey-planner-ojp-landing-page/)

映射保留计划时刻、可用的预测时刻、站台、交通方式与分段信息；缺失值保持未知。扩展契约时同步修改 `shared/` 及前端，不能把预测时刻误写为计划时刻。当前交通接口有 JWT 守卫，未来匿名游客需经受限礼宾服务调用，不能为接入 OJP 而直接去掉鉴权。

失败处理区分：凭证失败、限流、超时、解析失败和确实无可行路线。可配置 Transitous 降级，但必须标明来源与数据状态，避免将供应商故障转换为“没有路线”。OJP 路线查询与 OJP Fare 是两项接入任务，不意味着可以读取个人 SBB 账户或完成购票。

实施节点：第 1 周核验权限、契约和典型路线；第 3 周实现 provider 与配置；第 4 周接入推荐约束并验证故障处理；第 5 周观察实际覆盖、响应与调用成本。每个方向只在其选择实施后复用这项任务。

验收案例包括出发／到达时间查询、坐标／站点查询、步行接驳、换乘、跨日与夏令时、未知预测、超时与限流、供应商标识和密钥保护。真实数据验收需要有效 Key；固定样本只能验证解析与规则。

## 3. 身份、隔离与离线

- 游客可以匿名开始，但必须有私有会话与行程归属检查。
- 公共入口码不授予任何人的私有行程读取权限。
- 匿名访问如何接入 TREK 的用户模型，需要技术验证；不得共用一个普通用户账户绕过权限。
- 多机构试点优先实例、数据库、上传、缓存和备份隔离。
- 共享租户上线前需检查所有查询、文件、实时房间、令牌、插件、MCP、定时任务和恢复流程。
- 行程更新使用版本号和幂等键；离线确认在联网后重新核验。
- 快照显示时间，实时信息缺失时说明可用范围。

## 5. 商业实验共同规则

所有 CHF 价格是待测区间。访谈偏好、点击意愿、意向书、真实支付和续费分别记录，不互相替代。

小样本优先用人工报价或明确轮换实验，不宣称得出统计显著结论。真正的价格 A/B 测试需要足够样本、相同权益、随机分配和预设分析方法。

公开说明服务范围、计费周期、取消及退款条件。尚未实现的服务不能以自动完成的名义收费；付费人工服务明确交付时间与方式。

每个方向至少记录：获客成本、成交时间、每用户调用成本、内容和支持工时、实收收入，以及直接贡献。正贡献不等于覆盖研发与销售后盈利。

## 6. 六周资源假设

基准资源：一名熟悉项目的全栈开发者，一名访谈与内容协作者，有限区域与少量路线。需要外部主体批准时，六周只承诺试点与证据，不保证采购完成。

周计划必须有可审查交付物、必要测试与继续条件。前两周需求或数据不成立，可以停止或转向，不把失败验证变成扩大功能的理由。

## 8. 许可与数据保护

本系列默认采用 AGPL 衍生开源路线。修改版在线服务向用户提供对应源码；分发遵守相关义务。用户数据和凭证不属于要发布的源码。[AGPL](https://www.gnu.org/licenses/agpl-3.0.html)

使用独立品牌，保留仓库 `LICENSE`、`NOTICE.md`、`TRADEMARKS.md` 所要求的信息。闭源独立组件的边界需具体审查，不能靠目录或 API 分离推断。

数据保存期限是待确定产品政策。收集最少偏好，支持撤销与删除；不要求护照、诊断、完整日历或持续位置。个人明细默认不交给机构或商家。隐私政策和适用义务在试点前核对。

## 9. 证据记录方式

建立四种分离记录：来源事实、用户原话与行为、实验参数、实际结果。每次演示写清哪些是真实数据、哪些是固定样本。

竞品研究至少包含：现有替代工具、同类付费服务、人工解决方式，以及“不使用任何服务”的选择。未调查前不写“首创”“唯一”或“零竞争”。
