# 技术难度与工作量估算

> 日期：2026-10-06｜估算性质：基于局部代码阅读的工程判断，不是完成技术验证后的报价或工期承诺。

## 1. 估算口径

一工程人日按约六小时有效开发时间理解，包含该功能必要的调试、接口验证、测试与代码整理。日历时间还包含访谈、内容、外部等待与其他工作。

假设：一个地区、少量核验模板、单节点部署、有限语言，复用 TREK；开发者具有成熟生产工程经验，允许使用 AI 辅助；未验证 OJP Key 与真实响应，不训练新模型，不做自动购票。

下表是每项在相应基础已可用时的增量估算。存在共用模块，不能直接相加；依赖未满足时需要追加前置工作。范围反映未知，不表示上下界已通过实验验证。

## 2. 代码阅读发现

- `server/src/nest/transit/transit.service.ts` 已验证输入、调用供应商、缓存并转换交通段，但当前分发与 Google／Transitous 选择绑定，新增供应商需要调整。
- `server/src/nest/transit/google-transit.provider.ts` 可参考密钥、超时、缓存和统一数据转换模式，不等于可以不经修改地替换成 XML。
- `shared/src/admin/admin.schema.ts` 当前供应商集合为 `transitous`、`google`。新增 `ojp` 会影响共享校验、管理配置与前端标识。
- `TransitController` 使用 JWT 守卫。匿名游客接入需新会话和受限调用，不应通过移除鉴权解决。
- `client/src/sync/mutationQueue.ts` 依赖登录状态和现有资源映射。访客行程与建议确认不是自动获得现成离线写入能力。
- 已有 transit、weather、share、LLM 等测试可帮助回归，新协议与新业务边界仍需补充。
- 预订文本提取已有邮件与 PDF 基础，但自然语言偏好、截图和行程输入仍是独立流程。

这不是完整架构审计。尚未运行真实 OJP 请求、完成匿名身份技术验证或审查所有离线与权限链路。

## 4. OJP 适配器单独估算

有限查询原型：约 1–3 工程人日，前提是已获得可用 Key、官方请求样本和响应。

在现有模块内完成一个试点级 provider：约 5–10 工程人日，主要工作为：

| 工作 | 工作量组成 |
| --- | --- |
| 契约与样本 | 确认地点查询、路线规划、过滤支持及错误响应 |
| XML 请求／解析 | 命名空间、集合／单对象、可选字段和响应大小 |
| 数据映射 | 站点、步行段、交通段、计划与预测、站台和几何 |
| 系统接入 | Provider 枚举、Nest 注册、配置、密钥与前端标识 |
| 可靠性 | 限额、缓存、超时、来源、明确失败与可选降级 |
| 必要验证 | 坐标、到达查询、跨日、缺字段、错误与现有供应商回归 |

这是粗略总范围，不是每行独立加一天。默认不包含独立 GTFS-RT 订阅、OJP Fare、个人 SBB 账户读取、购票、全天后台监控或新匿名身份。

先做一天左右的数据与契约验证，再更新估算。若实际服务不支持某个过滤条件，需明确本地处理或缩减范围。

## 6. 数据与运营工作

假设已有少量合法来源、只做一个地区，第一批模板与地点核验可预留约 8–15 工作人日，另加持续维护；实际取决于地点数量、交通距离和信息缺失。

亲子、低体力与户外路线的关键现场核验可能更重。完整票券规则、实时商家容量、无障碍设施和精确观景质量均不能靠几段提示词补齐。

API 审批、酒店合作、现场天气、活动日期与采购周期是外部等待，不包含在工程人日中。现有真实数据是否覆盖与持续运行成本，均需小试验。

## 7. 三种整体范围

| 范围 | 工程估算 | 人工内容／验证 | 独立创始人日历时间 |
| --- | --- | --- | --- |
| 受限参赛演示 | 6–10 工程人日 | 少量固定内容，约 2–4 工作日 | 约 2–3 周 |
| 单地区、少量酒店可试用 MVP | 22–35 工程人日 | 约 8–15 工作日与访谈 | 通常 6–10 周，外部等待可能延长 |
| 十六项的受限集成试点版本 | 约 70–120 工程人日 | 更广内容与合作需另估 | 至少约 4–7 个月，不能作为正式报价 |

MVP 假设选择约束表单、OJP、核验模板、方案保存、来源说明、简单备选与员工编辑，延后共享租户、复杂多人、全面票价和全天监控。范围精简、输入用表单且账号受控时靠近下限；新匿名身份和真实住客运营靠近上限。

原六周计划是紧范围的验证路线，不代表独立创始人能在三十个工作日内同时完成全部开发、内容、销售与真实采购。AI 能帮助常规编码，但不会替代真实接口、领域边界和现场验证。

## 8. 建议的降低难度办法

1. 先用结构化表单，随后增加自然语言；这样可区分解析错误和推荐错误。
2. 首批路线人工编辑，规则筛选；避免开放式无限行程求解。
3. OJP 首版只做地点与路线请求，不同步开发票价与事件流。
4. 首版给现有账号或受限邀请使用；匿名会话完成后再扩大住客入口。
5. 一个地区、一个实例，先跑实际试点；共享租户与中央平台后续设计。
6. 先做页面内主动检查与人工确认，后续再做全天提醒与自动调整。
7. 先复用已有天气供应商核验试点覆盖；MeteoSwiss 新适配单独验证。

## 9. 下一项最有价值的技术验证

先用 1–2 工程人日完成 OJP 样本查询与现有交通协议映射，再用 1–2 日确认私有访客行程能否接入现有权限。这两项会显著缩小后续估算的不确定性。

当前尚未实施这些验证，估算应随结果更新。
