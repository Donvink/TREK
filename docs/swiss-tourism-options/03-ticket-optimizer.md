# 03｜瑞士交通票券与行程优化

> 方向：可解释的票券决策｜版本：v0.1｜日期：2026-10-06
>
> 所有价格与目标是实验假设。共同基础见 [00](00-common-foundation.md)。

## 1. 定位与首个问题

面向计划多日公共交通旅行的游客，将既定旅程、年龄类别、已有票券与可接受限制转化为几种购票方案，说明覆盖范围、估算成本和未知项。

首个客群是同一区域三至五日旅行者，优先服务旅行社或人工咨询入口。首版比较少量票券，不承诺全瑞士、全产品、全日期的最低价格。

问题假设：游客理解票券规则的成本较高，且有足够金额差异使其愿意付费。免费官方工具能解决多少问题，必须通过对照任务验证。

## 2. 发散方向

| 方向 | 用户任务 | 验证 |
| --- | --- | --- |
| 行程票券顾问 | 行程固定，比较票券组合 | 人工复核总价和覆盖 |
| 反向玩法推荐 | 通票已买，选择合适活动 | 不能为“用满”诱导不必要支出 |
| 家庭购票 | 年龄与同行条件不同 | 逐条确认适用条件，未知则不报价 |
| 灵活性比较 | 低价限制票和可变计划之间选择 | 同时展示退改、指定班次与风险 |
| 旅行社批量审查 | 为多个客人检查报价 | 看每案例工时与差错变化 |
| 住宿权益整合 | Guest Card 与其他票券重叠 | 从一家合作酒店开始核验 |
| 行程与费用联合调整 | 调整日期或景点减少支出 | 与固定行程版本分开展示 |

MVP 选择“固定行程、限定票券集合、可追溯估算”，先完成准确性，再做行程优化。

## 3. 产品设计

流程：填行程 → 填年龄类别与已有权益 → 确认每段出行 → 比较组合 → 查看覆盖与额外费用 → 跳转官方渠道购买。

页面包括行程审查、旅客类别、组合对比、逐段费用与假设、结果核验。用户年龄用适用区间，首版不收集生日或护照。

结果必须明确：何时取价、哪些费用包含、哪些项目待确认、是否限制班次、是否需要额外预订，以及最终购买渠道可能不同价。

保存结果为报价快照。更改旅程或条件后重新计算，不把旧结果继续称为最新。

## 4. 技术设计

复用 TREK 行程、交通段、预算与预订展示。新增 `TicketComparisonModule`，包含产品规则、报价适配、资格判断、覆盖矩阵与求解器。

| 对象 | 内容 |
| --- | --- |
| PassengerCategory | 适用年龄段、优惠资格、同行条件 |
| FareProductRule | 地域、日期、有效日、折扣、限制与来源 |
| JourneyLeg | 时间、运营方、路段、服务类别 |
| FareQuote | 价格、时间、约束、来源、报价状态 |
| CoverageMatrix | 产品对每段的全覆盖／折扣／不适用／未知 |
| ComparisonScenario | 假设、候选组合、基线、费用与差异 |

接口：`POST /api/tickets/scenarios`、`POST /api/tickets/scenarios/:id/compare`、`GET /api/tickets/scenarios/:id/breakdown`。

### 4.1 求解与正确性

将日票、连续或灵活有效产品及逐段票转换为覆盖关系，先枚举限定规模组合。对每个组合计算产品费用、未覆盖路段与折扣后费用，检查日期与旅客资格。

硬规则缺失就标记未知，不用默认折扣填补。未知组合可供人工核验，不参与“已验证最便宜”排名。

以同样乘客、路线、日期、车厢和灵活性比较基线。省钱额不能用不同权益或未计费用制造。

### 4.2 数据接入

OJP Fare 是可验证入口，官方说明报价不具约束力且查询受限。第一周确认可申请产品、请求契约、样本价格及覆盖，不假设通票与所有山地项目均包含。[OJP Fare](https://api-manager.opentransportdata.swiss/portal/catalogue-products/tedp_ojpfare-1)、[官方说明](https://opentransportdata.swiss/en/cookbook/open-journey-planner-ojp-landing-page/)

已验证规则人工版本化维护；不能通过绕过访问限制获取动态价格。AI 仅解释计算结果，不计算适用资格或创造价格。

测试票券日期边界、年龄条件、已有权益重复计价、两产品重叠、未知报价、失效报价和币种单位。

### OJP 适配器接入（新增任务）

在现有 `server/src/nest/transit/` 中增加 OJP 2.0 provider，服务端转换为现有交通协议，复用前端接口。为票券比较提供经验证的交通段；OJP Fare 的报价能力单独接入。

第 1 周验证权限与样本，第 3 周实现 provider 与配置，第 4 周联动业务约束及失败降级。尚未实现；完整鉴权、字段、缓存与验收见 [共用 OJP 设计](00-common-foundation.md)。

## 5. 六周计划

| 周 | 工作 | 交付与门槛 |
| --- | --- | --- |
| 1 | 访谈 10 位游客和 3 家机构；申请／核验票价数据 | 产品白名单、可用报价样本；不通则改人工服务 |
| 2 | 手工完成 15 个行程比较 | 每段来源与独立复核；建立边界案例 |
| 3 | 规则库、覆盖矩阵、限定枚举求解 | 测试集与结构化比较结果 |
| 4 | 对比页面、逐段明细、假设和官方购买入口 | 用户理解测试；未知条件不能进入确定排名 |
| 5 | 约 20 个真实报价任务，收取人工或工具费用 | 报价准确性、支持工时与付款 |
| 6 | 独立复核、商业复盘、参赛材料 | 对照官方购买条件的差异报告与演示 |

六周成功产出可以是高质量人工增强工具，不必是全国自动购票引擎。

## 6. 收费实验

| 模式 | 价格假设 | 交付 | 检验 |
| --- | --- | --- | --- |
| 单行程比较 | CHF 9／19 | 限定产品的明细与建议 | 在明确覆盖条件下是否支付 |
| 人工复核 | CHF 39–69 | 工作时间内复核与解释 | 付费是否足以覆盖核验工时 |
| 机构工具 | CHF 149–299／月 | 限定案例数、导出及规则更新 | 每案例节省工时和采购 |

“省钱后分成”留到能验证基线与归因时再考虑。收取费用不能依赖夸大节省额。首版购买和售后仍由官方渠道承担。

## 7. 验证与停止

建议建立至少 30 个覆盖不同边界的复核案例，核心白名单规则不能存在已知错误。未知覆盖率单独统计，不通过删掉困难案例提高准确率。

实际比较指标：完整可比较案例比例、价格差异、发现错误数、解释理解率、人工工时和支付率。

若完整案例很少、访问条件不适合或更新负担无法覆盖收入，停止自动“最优”定位，转向人工票券审查或限定区域权益说明。

## 8. 参赛准备

拟选 Consumer Solutions，机构版按当届分类确认。

- 创新：跨产品覆盖、资格与灵活性的可解释组合决策，而非简单查票价。
- 团队：交通规则专家或复核协作者、数据与求解能力。
- 技术：覆盖矩阵、未知处理、版本化规则与独立样本验证。
- 市场：有复杂旅程的客群、当前官方工具的不足与机构流程。
- 影响：减少理解负担和错误购买；不用推导未经测量的减排。
- 商业：付款、支持成本、产品覆盖扩张的维护成本。

演示：同一旅程比较两三组合 → 展开路段 → 修改已有票券 → 费用更新 → 一个未知项目正确显示待确认。公布真实核验过程，避免声称全球最低价。
