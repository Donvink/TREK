# 02｜天气与交通动态行程助手

> 方向：旅行过程中的条件变化处理｜版本：v0.1｜日期：2026-10-06
>
> 共同约束见 [基础文档](00-common-foundation.md)。所有指标和收费均待验证。

## 1. 定位与问题

服务已有行程的游客：天气、交通或营业状态变化后，识别受影响活动，在保留固定预约的前提下给出可解释替代方案。

首个客群是同一区域停留两三天、包含城市和户外活动的游客。先覆盖低风险观光，不承担登山、滑雪等安全判断。

关键假设：游客会愿意提供原行程；变化足够频繁；替代方案比自行调整更省时间；用户愿意支付“出行过程中持续支持”的费用。

## 2. 发散方向

| 延伸 | 具体能力 | 商业与验证 |
| --- | --- | --- |
| 雨天替代 | 户外与室内活动互换 | 天气变化前后询问采用情况 |
| 交通中断调整 | 关键换乘失效后的重排 | 先做已知样本，之后观察真实事件 |
| 体力临时下降 | 缩短步行与减少地点 | 测用户是否觉得更轻松、是否走完 |
| 多日顺序优化 | 交换活动日期，保留酒店 | 比较受锁定项目影响的可行方案 |
| 旅行社售后助手 | 机构为客户处理变化 | 测服务人员每案例时间与付费 |
| 活动运营方通知 | 已知取消后给替代 | 必须有可信运营来源与权限 |
| 陪同家属独立方案 | 主行程固定，同行人另行活动 | 后续验证，不增加首版复杂度 |

MVP 先“天气影响 + 用户主动改体力”，交通事件视数据验证结果加入。即使没有真实中断，也能测试规则，但必须区分模拟演示与实际效果。

## 3. 产品设计

游客导入或填写简化行程 → 标记已预订、必须保留、可调整 → 设定时间与体力 → 查看条件检查 → 比较建议 → 确认新版本。

页面包括行程检查页、活动锁定页、建议对比页与版本历史。建议卡必须解释原因、替代收益、变化费用和仍需外部确认的事项。

首版支持手动行程和 TREK 内行程，预订解析可作为辅助；解析后时间与地点由用户确认。外部预订不自动改变，已出票或有退改限制的项目必须保留其状态。

状态：未检查、正常、需要核验、建议调整、已知不可用、数据不足。未检查或无数据不能显示正常。

首版页面内提醒；需要后台主动通知时，另行获取邮件或 Web Push 授权。

## 4. 技术设计

### 4.1 复用与模块

复用已有行程、预订、天气、交通、实时更新与离线机制。新增 `AdaptivePlanModule` 管理规则、状态快照、建议与版本。

| 对象 | 字段与职责 |
| --- | --- |
| ActivityConstraint | 时间窗、可调等级、预约锁、体力、来源 |
| ConditionSnapshot | 天气或交通事实、取数时间、有效期 |
| ImpactAssessment | 受影响活动、规则、严重程度、未知信息 |
| ChangeProposal | 基准版本、替代活动、差异、失效时间 |
| PlanVersion | 确认后的快照与审计原因 |

接口：`POST /api/adaptive/plans/:id/check`、`GET /api/adaptive/plans/:id/proposals`、`POST /api/adaptive/proposals/:id/accept`、`POST /api/adaptive/proposals/:id/reject`。

### 4.2 求解方法

只对受影响窗口做局部重排，保留锁定项目和酒店日期。按硬约束过滤替代模板，再按少改动、舒适度与用户偏好排序。

若无法满足锁定项目，不擅自解除锁；展示“没有可行替代”以及需要用户决定的冲突。规则解释绑定数据版本，不让 AI 自行宣布活动取消。

### 4.3 调度与一致性

打开页面时刷新，近期活跃行程按限额后台检查，同位置天气和交通可共享公共事实缓存。个人建议缓存需要按用户和版本隔离。

确认采用事务、版本号与幂等键。原行程变动、数据过期或建议失效时拒绝旧确认并重新生成。离线确认联网后重检。

### 4.4 测试与降级

测试锁定预约、跨日交换、夏令时、过期预报、缺失实时状态、并发确认与重复点击。供应商故障时保留原行程，不伪造新状态。

新增 MeteoSwiss 或 OJP 适配必须先做契约样本验证，见 [数据基础](00-common-foundation.md#4-外部数据)。

### OJP 适配器接入（新增任务）

在现有 `server/src/nest/transit/` 中增加 OJP 2.0 provider，服务端转换为现有交通协议，复用前端接口。重检受影响交通连接，保留固定预约并生成替代建议。

第 1 周验证权限与样本，第 3 周实现 provider 与配置，第 4 周联动业务约束及失败降级。尚未实现；完整鉴权、字段、缓存与验收见 [共用 OJP 设计](00-common-foundation.md)。

## 5. 六周计划

| 周 | 工作 | 交付与判断 |
| --- | --- | --- |
| 1 | 访谈 15 位游客和 3 家旅行服务机构，获取过去变更案例 | 至少 10 个匿名案例；区分常见问题和极端事件 |
| 2 | 人工处理变化，验证天气／交通接入 | 5–10 次调整记录；核定首版事件类型 |
| 3 | 约束、锁定、快照与局部推荐 | 样本行程变更流程，硬约束测试 |
| 4 | 版本确认、对比、降级与提示 | 数据失败也能打开原计划；确认一致性测试 |
| 5 | 限定区域试点、真实收费与成本记录 | 15–30 个行程；模拟与真实事件分别记录 |
| 6 | 事件复盘、用户采用验证、参赛演示 | 可追溯案例、真实价值、数据覆盖报告 |

若第二周发现条件数据无法稳定接入，收敛为用户主动触发的调整服务，不继续宣称实时自动处理。

## 6. 收费实验

| 实验 | 价格假设 | 服务范围 | 验证 |
| --- | --- | --- | --- |
| 单次旅程支持 | CHF 9 与 CHF 19 | 最多三日、限定检查次数和区域 | 游客支付及实际使用 |
| 人工增强调整 | CHF 29–49／旅程 | 工作时间内人工确认，明确响应时间 | 是否为可靠支持付费 |
| 机构订阅 | CHF 149–399／月 | 限定客户行程数与支持额度 | 服务人员节省工时与真实采购 |

价值对比包含免费天气与交通查询，不只比较人工旅行顾问。若用户仅愿意为人工保证付费，先经营人工服务，不以 AI 自动化承诺代替。

## 7. 指标与决策

记录有效变化数、提出建议数、展示数、接受数、实际采用数、错误状态与每次人工核验时间。

初始复盘目标：至少 10 个有效变化案例，其中若不足真实案例，应延长观察；建议接受率可暂定 40%，但必须报告样本与用户自选偏差。

“节省时间”通过用户原方案与处理过程对比测量，不能用生成速度代替。出现确定性事实错误，优先修复规则与数据；若长期只能给通用提示，调整产品定位。

## 8. 参赛准备

拟选 Consumer Solutions；机构运营方案是否属于其他类别按实际表格确认。

| 维度 | 证据 |
| --- | --- |
| 创新 | 条件变化、固定预约和局部重排的结合 |
| 团队 | 数据接入与旅行服务经验，核验责任 |
| 技术与产品 | 可复现实例、状态与版本一致性验证 |
| 市场 | 哪些旅程频繁变化、游客与机构谁支付 |
| 影响 | 用户时间与体验改善；无未经测量减排承诺 |
| 商业 | 单次支付或机构付费、支持与调用成本 |

演示：原三日行程 → 锁定预约 → 输入明确标识的天气变化样本 → 比较替代 → 确认 → 用过期版本再确认并展示正确拒绝。真实案例单独呈现，不与模拟混合。

## 9. 主要风险与下一步

风险是无可靠变化信息、误把不适宜当作取消、自动建议触及不可改预订。先确定一个事件类型、一个区域及核验人。
