# 中文旅行规划原型：确认方案与实施计划

> 2026-10-06｜grilling 已结束，用户已确认进入实施计划。
> 本文为本轮实施依据；优先于旧的瑞士假期、酒店与十方向方案。功能尚未实现，验收门槛是计划，不是结果。

## 1. 确认目标与边界

先做创始人自己能用的本地产品，以原型、演示视频和后续验证计划参加 >>venture>> 2027。第一批目标用户是从瑞士出发旅行的中文用户，覆盖瑞士境内及一条意大利跨境案例。暂不开展外部用户招募；个人案例不能作为市场需求或收入证据。

核心问题：小红书攻略太多太杂，用户不知道哪些地点适合自己，也难以把景点、住宿和公共交通拼成完整行程。首要差异假设是更符合个人兴趣的筛选与取舍解释；若同素材的通用 AI 同样好，则转向检验交通核验与完整流程的价值，不宣称已证明推荐优势。

| 决策 | 已确认范围 |
| --- | --- |
| 输入 | 简短偏好问题；已有收藏可选补充；没有收藏也可自动搜索 |
| 采集 | 复用 [rednote_mcp](https://github.com/Donvink/rednote_mcp)，在创始人电脑运行，使用本人的本地登录会话 |
| 候选 | 三个按体验侧重区分的方案；遵守同一预算和体力约束 |
| 个性化 | 收藏作为灵感，可以推荐收藏外地点，解释选择与排除理由 |
| 长期偏好 | 参考 career-ops：跨行程画像与偏好信号随使用积累；推断只提建议，用户确认才写入（2026-10-21 新增，设计见 [设计文档 5.1](personal-travel-guide-assistant-design.md)） |
| 完整攻略 | 选定方案后展开每日安排、地图、公共交通、住宿建议 |
| 交通 | 路线、预计费用、可能适用的票券提示；精确全票种最低价不进入首版 |
| 住宿 | 区域建议＋少量具体酒店链接；环境与交通依据可追踪；佣金不影响排序 |
| 信任 | 推荐理由、来源、核验时间、未确认事项；未知选项可保留，提供已核验替代 |
| 冲突 | 时间、交通、价格按适用日期官方信息核验；体验评价保留不同意见 |
| 天气 | 用户主动刷新，展示影响与替代建议，确认后更新；固定住宿和交通锚点保留 |
| 图文 | 固定模板生成攻略卡片，支持修改、下载，由用户自行发布 |
| 运行 | 本地完整运行，允许等待几分钟，显示阶段与失败原因；参赛交付演示视频 |
| 投入 | 独立开发，每天至少 5 小时；Codex/Claude Code 辅助开发；额外现金不超过 CHF 50 |
| 许可 | 接受 TREK AGPLv3 对应源码要求；保留版权、署名，独立产品品牌 |
| 商业假设 | 规划免费，尝试住宿或活动预订佣金；尚无合作渠道、真实下单或收入证据 |

## 2. 两个验收案例

## 3. 技术接入方式

### 3.1 先复用，新增最少的业务链路

当前代码已有行程与日期模型、地图、公共交通代理、天气查询和 LLM 调用基础。实施入口：

- `server/src/nest/trips/`、`shared/src/trip/`、`shared/src/day/`：复用保存行程与日期结构。
- `server/src/nest/transit/`：先测试现有 Transitous 在两条案例上的覆盖；不能把有接口等同于有 Turin 完整数据。
- `server/src/nest/weather/`：复用查询，但攻略端明确区分预报、历史、季节参考与未知。
- `server/src/nest/llm-parse/`：复用配置和客户端基础；新增旅游内容输出协议，不能直接沿用预订解析提示词。
- 前端复用现有地图与行程编辑；新增偏好入口、三方案比较、来源视图、调整确认和卡片预览。

瑞士 OJP 保留为交通覆盖不足时的候选适配，不作为首版全部功能的前置依赖；意大利段覆盖必须独立验证。交通缺失时提供官方查询链接和人工录入核验记录；未查证的连接不能标为可执行。

### 3.2 本地采集与产品解耦

现有 `rednote_mcp.py` 包含关键词搜索、帖子读取和浏览器登录；代码阅读不能代替实际成功率验证。

第一步用独立采集进程输出版本化 JSON，TREK 导入该文件。跑通后再接本地只读任务适配器；不把 Python 浏览器逻辑嵌入 Nest 请求。浏览器会话留在爬虫本地目录，不进入 TREK 数据库、源码、日志或演示材料。

只接搜索和读取能力。帖子发布、评论等能力不接入旅行流程。采集阶段记录成功、缺失和失败；遇到登录失效或访问限制，暂停并报告，不无限重试。已有缓存可继续用于明确标注的离线演示，不伪装成最新采集。

### 3.3 建议的数据契约

| 对象 | 最小信息 |
| --- | --- |
| SourceNote | 原始链接、标题、正文/摘要、发布时间（可未知）、采集时间、可用状态、内容指纹 |
| PlaceCandidate | 地点名称、标准地点/坐标、兴趣标签、原文证据、来源集合、消歧状态 |
| TravellerPreferences | 日期、起终点、人数、预算口径、兴趣、体力、交通、必须去/排除项；默认值取自画像 |
| TravellerProfile | 按账户保存的长期偏好条目：内容、来源等级（明确/行为/推断）、依据、置信度、更新时间 |
| PreferenceSignal | 只追加的事件：方案选择/拒绝及原因、锁定/排除、修改、行后复盘；关联行程与方案 |
| VerifiedFact | 类型、事实值、适用日期、官方链接、查询时间、核验方式、已核验/未知/冲突 |
| TripOption | 体验主题、地点与住宿分布、粗估费用、交通负担、取舍解释、未知事项 |
| ItineraryVersion | 每日活动与交通、固定锚点、核验记录、预算区间、版本 |
| HotelSuggestion | 酒店/区域、适合理由、位置证据、价格状态、预订链接、商业合作标记 |
| ShareDraft | 对应行程版本、卡片字段、编辑内容、素材来源、过期状态 |
| PlanningRun | 阶段、时间、模型/查询成本、缓存命中、错误、可重试状态 |

按来源和采集时间缓存抽取结果；查询缓存包含旅行日期、地点及相关条件。外部帖子只作为数据，不执行其中指令。来源正文与截图不默认成为可再发布素材。

硬约束由程序检查：时间重叠、交通接续、返回期限、营业时间、固定住宿、预算口径。信息缺失须显式报告；模型可以解释和提出备选，不能补造班次、票价和空房。

## 4. 200 小时实施顺序

以下为规划估计，不是交付保证。每天至少 5 小时提供约 275 小时日历容量；按 200 小时任务安排，其余用于学习、失败重试、休息和缓冲。每阶段评估剩余时间，先缩小地点覆盖，保留已确认完整流程。

| 阶段 | 建议日期 | 小时 | 具体交付与完成条件 |
| --- | --- | ---: | --- |
| 1. 运行与数据验证 | 10/06–10/10 | 16 | 本地 TREK 可运行；爬虫读取两地少量真实样本；逐段检查交通覆盖；确定可调用的模型和成本记录；列出失败及缺口 |
| 2. 素材协议与地点抽取 | 10/11–10/17 | 24 | JSON 导入、去重、地点消歧、来源视图；人工检查两个案例的样本，记录错误；采集失败可明确停止 |
| 3. 偏好与三方案 | 10/18–10/24 | 28 | 表单、三个体验方案、取舍解释；用户可锁定或排除地点；记录首轮与通用 AI 的同素材比较；偏好表单写入长期画像，选择/拒绝/锁定记为 PreferenceSignal |
| 4. 每日行程与核验 | 10/25–11/03 | 42 | 选中方案保存为 TREK 行程；关键交通、时间及住宿锚点检查；区域与酒店链接；未知记录及替代方案；能检查两案 |
| 5. 天气调整 | 11/04–11/08 | 22 | 主动刷新、影响与备选、确认应用；不改固定住宿；修改后重新检查衔接；明确模拟或真实数据 |
| 6. 图文导出 | 11/09–11/13 | 22 | 固定卡片模板、文字修改、下载；取自当前行程版本；行程修改后提示卡片过期；使用原创或可用素材 |
| 7. 双案例验收与修复 | 11/14–11/19 | 22 | 两案完整走通；匿名标签比较推荐；人工核验关键衔接；测试失败与成本上限；记录尚未解决问题 |
| 8. 参赛证据与视频 | 11/20–11/24 | 24 | 演示视频、功能状态表、案例记录、开发来源说明、英文申请草稿及后续验证计划 |
| 缓冲与提交 | 11/25–11/30 | 另留 | 修复提交阻塞、核对申请表与官方截止；用户审核最终内容后再提交 |
| **合计** | | **200** | |

长期画像在 200 小时内只做最小部分：画像与信号的存储、表单读写画像、事件记录。画像整理、“是否记录此偏好”的校准建议、行后复盘界面和 MCP 只读开放在核心流程完成后再排期，不挤占双案例验收。

每阶段交付能运行的纵向流程。第三阶段先用已核验的小素材库贯通；不能为了完成大规模采集而推迟推荐和验收。若爬虫当前无法工作，先修复少量样本采集并如实记录；本轮授权的目标仍是自动采集，不把手工粘贴悄悄替换为最终能力。

## 5. 成本和模型决策

CHF 50 是额外支出的硬上限。建议最多 CHF 35 用于模型测试和推理，CHF 15 预留；地图与数据优先测试现有免费接口及其适用条件，不先购买服务。记录请求量、重试、单次成本和累计费用，新增付费请求到上限时停止。

开发助手与运行时推理分开规划。第一阶段核对已具备的程序化模型调用方式及实际计费；不把开发订阅自动当作应用可用的 API 预算。若本机性能允许，测试现有本地模型路径；否则使用预算内 API、缓存与少量样本。预算不足时降低采集规模与重算次数，并清晰区分离线回放与实时生成。

生成任务采用有上限的重试、阶段进度、取消与失败提示。缓存和模板减少无意义调用，不能靠取消核验来节省成本。

## 6. 验收与证据

### 6.1 推荐质量是首要指标

对两案分别固定素材、偏好和提示信息。将产品与通用 AI 结果隐藏来源标签，由创始人逐项记录：是否想去、偏好匹配原因、取舍解释是否有依据、是否存在重复地点或虚构内容。创始人仍有参与开发造成的偏差，结果不能称为独立用户研究。

记录候选接受率、拒绝原因、修改次数和比较偏好；不预先编造提升百分比。同素材条件下未见优势，则按已确认决策改写参赛差异，重点展示核验和完整流程，并继续检验该价值。

### 6.2 完整流程必须通过

- 两案均能输入偏好、生成三个可比较方案、展开并保存每日行程。
- 核心交通与时间安排逐项人工检查，无已知会影响成行的错误；尚未核验的行程不能标成完整可执行。
- 每项关键事实有来源、适用日期、查询时间和核验状态；主观体验与官方事实分开显示。
- 酒店链接可打开；推荐依据与商业关系明确；有链接不等于实时可订或有佣金。
- 雨天或交通缺失等测试情境可给备选，不破坏住宿、返程等锚点。
- 卡片可修改、下载，内容与已确认行程一致；计划攻略不写虚构亲历体验。
- 登录失效、空结果、模型失败、预算用尽时可停止并解释，不产生伪造的成功结果。

实现时对关键逻辑写有价值的测试：地点消歧、未知/冲突传播、时间接续、固定锚点、版本更新和成本限制。用两案做端到端检查。按改动范围运行相关 Vitest、类型检查及必要构建，不为纯文档更新运行应用测试。

证据目录建议后续建立 `docs/travel-prototype-evidence/`：保存输入条件、来源清单、脱敏采集样本、结果版本、人工核验记录、比较记录、成本表和功能状态。当前不生成任何虚假的使用/收入记录。

## 7. 参赛与后续商业验证

用户已确认居住瑞士，并有未来在当地注册公司和开展主要研发的意愿；主要居所等事实及完整资格仍以申请时的真实信息和官方条款为准。初始申请截止为 2026-11-30 23:59 CET，入围后才提交后续商业计划等材料。

参赛叙事围绕“中文旅行者把零散灵感变成有依据、可调整的公共交通行程”。如实披露 TREK 底座、rednote_mcp 既有工作与本次新增功能；未完成的接口、未证明的推荐优势、佣金渠道及市场需求均列为假设。个人使用验收不写成已获得客户。

后续验证计划：原型之后再招募目标用户，比较推荐质量、额外查证、实际采用与预订入口使用；验证佣金渠道及每单收入、成本后再谈商业可行性。当前不要求提前招募，也不把“计划免费”推导成已证明收入模式。

许可遵守仓库 AGPLv3 第 13 条及分发要求；公开对应源码前剔除登录会话、个人旅行资料和密钥，保留品牌与素材署名。原型阶段完成授权素材核查；未来规模化采集另核对允许范围与运营条件。
