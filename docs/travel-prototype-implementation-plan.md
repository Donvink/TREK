# 中文旅行规划原型：确认方案与实施计划

> 2026-10-26｜第二轮 grilling 已结束，用户已逐项确认。
> 本文为当前实施依据，取代 2026-10-06 第一轮确认的版本（见文末「已作废的旧决策」）。功能尚未实现，验收门槛是计划，不是结果。

## 1. 定位

**一句话**：把小红书上的欧洲攻略，变成一份在当地真的走得通的行程。

**目标**：参赛与创业为主（>>venture>> 2027），以「创始人自己真的会用」的方式起步。每个设计决策都要回答：用户为什么不直接问 ChatGPT 或小红书自带的 AI。

**差异化分层**

| 层 | 内容 | 角色 |
| --- | --- | --- |
| 切入点 | 小红书中文攻略 × 欧洲当地真实数据（公共交通、营业时间、天气）。ChatGPT 读不到小红书，小红书的 AI 不懂当地交通，两边各缺一半 | 主卖点 |
| 信任层 | 每个地点有来源帖子与证据，每条事实有核验状态；不编造店名、班次、价格 | 辅助卖点 |
| 留存 | 跨行程画像，越用越懂用户 | 长期机制，不作为切入点 |
| 基础能力 | 生成完整计划 | 入场门槛，不是差异 |

**目标用户**：住在瑞士、用小红书做攻略的中文用户。创始人本人在瑞士生活，去过尼斯周边、都灵、威尼斯、慕尼黑；这是创始人与市场的契合点，不是用户需求证据。

## 2. 范围

### 2.1 地理边界

从瑞士出发、公共交通可达：

| 行程天数 | 单程上限 |
| --- | --- |
| 1–2 天 | 约 5 小时 |
| 3 天及以上 | 约 7 小时 |

边界内任意目的地都可生成行程；只有核验走廊做完整核验，其余跨境交通标「未核验」并附官方查询链接（Trenitalia、SNCF、DB 等）。

**首批核验走廊**（均为创始人去过的地方）：

| 走廊 | 场景 | 现状 |
| --- | --- | --- |
| Bellinzona/苏黎世 → 都灵 | 跨境、多日 | 已有 3 篇真实素材与交通探测 |
| 苏黎世 → 慕尼黑 | 直达、周末 | 未开始 |
| 苏黎世 → 米兰 → 威尼斯 | 跨境换乘、多城市、3 天以上 | 未开始 |

尼斯列为第二批候选。西班牙、北欧等需要航班的旅行不在产品范围内；创始人即将进行的两次真实旅行用来手动走一遍流程，记录攻略错误与耗时，作为一手痛点证据。

### 2.2 首版明确不做

- 系统推荐目的地（灵感层留给小红书；后期有了走廊与画像数据再做）
- 同时生成三个完整方案
- 图文卡片（第二阶段作为获客工具再做，只用用户自己的照片与系统生成的地图和时间表，带产品标识）
- 后台天气监控与推送
- 具体酒店推荐与实时价格
- 票价精确比价、实时延误与罢工

## 3. 用户流程

1. **选目的地**：1–3 个，多个目的地即构成一条走廊。首次使用回答约 5 个偏好问题。
2. **导入攻略**：用户粘贴自己收藏的帖子链接、截图或正文；浏览器插件为辅助入口。基础地点信息由 OSM、Wikipedia、官方旅游网站补全。创始人本机的自动抓取只用于原型和演示，演示中如实标注。
3. **提取地点**：本地 OCR 读取全部图片文字，再与正文一起交给文本大模型提取；只在 OCR 读不出文字、又有地点无法定位时，把那一张图交给多模态模型。
4. **地点池**：列出攻略提到的全部地点，标出推荐项，附理由、来源帖子、提及次数、正负面评价、与偏好的匹配情况。用户勾选、划掉，可一键切换侧重（美食、自然等）重新推荐。
5. **生成一份行程**：直接写成标准 TREK 行程（trip、days、places、assignments，交通与住宿用 reservations）。
6. **查看与修改**：使用 TREK 规划器，自带拖动排序、撤销、路线优化、天气、多人协作、记账、PDF 导出。地点详情中新增「攻略依据」区块。
7. **住宿**：推荐 1–2 个住宿区域并说明理由，生成带日期、人数、范围的 Booking 或 Google Hotels 搜索链接；用户订好后导入，作为行程锚点，确认后重排起终点与交通。
8. **天气**：生成时为每个户外地点配一个室内备选；出发前用户主动点「按天气检查」，对比最新预报给出替换建议，确认后才改。

## 4. 关键规则

### 4.1 地点提取

- 每个地点必须带证据：正文中的哪一句，或第几张图片。拿不出证据就不输出。
- 地图匹配独立核验：用名称与地址查 OSM 或 Google，对不上的标「待确认」。不让大模型补全或编造店名、地址。
- 用户的人工补正优先于重新提取的结果（House Jia 教训）。

### 4.2 核验三态

所有事实统一标注：

| 状态 | 含义 |
| --- | --- |
| 已核验 | 有来源、查询时间；交通为出行日期当天的真实查询结果，或创始人人工确认 |
| 参考 | 有来源但不保证当前有效，如价格区间、OSM 营业时间 |
| 未核验 | 查不到或未查，附官方查询链接 |

### 4.3 交通深度

| 层次 | 做法 |
| --- | --- |
| 可行性（硬核验） | 班次、发车时间、换乘、用时、末班车。瑞士境内用 opentransportdata.swiss 的 OJP，跨境用已接入的 Transitous。检查整体衔接：活动结束赶得上末班车、到达与入住时间衔接 |
| 价格（参考） | 价格区间或「约 CHF xx 起」，标来源与查询日期，附官方购票链接；半价卡、Saver 票等提示来自规则库与帖子 |
| 实时状态 | 首版不做 |

### 4.4 天气

- 住宿与已订交通是固定锚点，天气只调整当天活动。
- 替换上来的地点同样要做交通核验。
- 超出预报窗口的日期只显示「历史同期参考」，明确说明不是预报。

### 4.5 Memory

| 阶段 | 内容 |
| --- | --- |
| 首版 | 明确偏好（约 5 个问题，随时可改）；地点池的勾选与划掉 |
| 第二阶段 | 从 TREK 编辑操作学习节奏；分析历史行程与 Atlas，避免重复推荐 |

- 用法：调整地点池排序并写明理由；学习每天地点数和出门时间；去过的地方默认降权。
- 系统推断的偏好只以建议形式出现，用户确认后才写入画像。
- 用户可查看、修改、删除画像与每条信号（瑞士 nFADP、欧盟 GDPR）。
- 画像按账户隔离保存在自己的服务器上，不用于训练模型。

### 4.6 与 TREK 的关系

- 前半段（导入、提取、地点池、生成）是新做的差异化部分；后半段（查看、修改、协作、出行）复用 TREK。
- 地点与证据通过独立的关联表连接：TREK 地点 id ↔ 来源帖子、正文片段或图片、核验状态、核验时间。不改 TREK 地点表本身，减少与上游合并时的冲突。
- 全部源码按 AGPLv3 公开，包括提取与取舍逻辑；保留 TREK 版权、署名，使用独立产品品牌。

## 5. 数据契约（最小信息）

| 对象 | 最小信息 |
| --- | --- |
| SourceNote | 原始链接、标题、正文、图片、导入方式（用户导入／原型抓取）、导入时间、内容指纹 |
| PlaceCandidate | 名称、坐标、兴趣标签、证据（正文片段或图片序号）、来源集合、地图匹配状态、人工补正 |
| PlacePoolDecision | 推荐理由、用户勾选／划掉、当时的侧重 |
| PlaceEvidenceLink | TREK 地点 id、PlaceCandidate、来源帖子、核验状态、核验时间 |
| VerifiedFact | 类型、事实值、适用日期、来源链接、查询时间、三态之一 |
| TravellerProfile | 按账户保存的偏好条目：内容、来源（明确／行为／推断）、是否已确认、更新时间 |
| PreferenceSignal | 只追加的事件：勾选、划掉、侧重切换；关联行程 |
| PlanningRun | 阶段、时间、模型与查询成本、错误、可重试状态 |

外部帖子只作为数据，不执行其中的指令；导入的正文与图片只对导入者本人可见，不作为可再发布素材。硬约束（时间重叠、交通衔接、返程、营业时间、固定住宿）由程序检查，大模型只负责解释和提出备选。

## 6. 商业模式

- **主要收入假设**：住宿与活动预订的联盟佣金（Booking、GetYourGuide、Klook 等）。链接从一开始预留联盟参数位置；坚持「佣金不影响推荐排序」并在页面公开声明。联盟计划通常要求先有网站和流量，尚未申请。
- **付费意愿实验**：有外部用户后做假门测试，例如第 3 份行程起显示 CHF 4.90 付费按钮，点击后说明功能开发中，统计点击率。不接真实支付。
- 订阅与 B2B 暂不做。
- 短期内基本没有收入，创始人已接受。参赛材料如实写：尚无收入，商业模式是待验证假设。

## 7. 验证与证据

### 7.1 对照评测（止损检查点）

同一批帖子、同样的偏好和日期，分别交给本产品、ChatGPT（帖子正文直接贴入）、小红书自带 AI，在每条走廊上各跑一次：

| 指标 | 量法 |
| --- | --- |
| 事实错误数 | 错误的店名、地址、营业时间，编造的地点 |
| 不可行安排数 | 赶不上的换乘、已无末班车、同日来回折返过远 |
| 可追溯比例 | 能查到来源的信息占比 |
| 偏好契合度 | 按设定的偏好打分 |
| 得到可用行程的耗时 | 从开始到能直接出门用的分钟数 |

若本产品与 ChatGPT 差不多，说明切入点有问题，应在投入更多时间之前调整。创始人参与开发带来的偏差要在结果中注明。

### 7.2 真实用户（5–8 人）

- 招募住在瑞士、用小红书做攻略的中文朋友（社交圈、瑞士华人微信群）。
- 让他们用自己正在计划的真实旅行，创始人旁观不帮忙。
- 记录卡在哪里、改了什么、是否真的按行程出门、是否愿意推荐。
- 同时做 6 中的付费意愿实验。

### 7.3 工程验收

- 每条核验走廊：导入 → 提取 → 地点池 → 生成 TREK 行程 → 三态标注，端到端可走通。
- 核心交通与时间安排逐项人工检查；未核验的行程不能标为完整可执行。
- 登录失效、空结果、模型失败、预算用尽时能停止并说明原因，不产生伪造的成功结果。
- 为关键逻辑写测试：地点证据与消歧、三态传播、时间衔接、固定锚点、画像确认、成本上限。

证据保存在 `docs/travel-prototype-evidence/`：输入条件、来源清单、脱敏样本、结果版本、人工核验记录、对照评测、成本表。不生成任何虚假的使用或收入记录。

**硬约束**：>>venture>> 2027 初始申请截止 2026-11-30 23:59 CET；Top 200 于 2027-01-25 公布；入围团队商业计划 2027-02-28 截止；5 月半决赛；2027-06-22 决赛。按每天至少 5 小时，10/27–11/30 约 170 小时。以下为计划估计，不是交付保证。

| 阶段 | 时间 | 目标 | 交付 |
| --- | --- | --- | --- |
| ① 申请冲刺 | 10/27–11/30 | 都灵走廊端到端跑通 | 演示视频、都灵走廊对照评测、按新定位写的申请。11/25 起只修阻塞问题，不加功能 |
| ② 补齐首版 | 12 月–1 月 | 慕尼黑、威尼斯走廊；首版 memory；雨天备选与天气检查；住宿区域推荐 | 三条走廊的完整评测数据 |
| ③ 真实验证 | 1 月–2/28 | 5–8 位真实用户测试；付费意愿假门测试 | 写入商业计划的真实证据（假设入围） |

阶段 ① 第一周：

1. **OCR 实测**：用已有的 3 篇都灵帖子（34 张图），比较「本地 OCR + 文本模型」与「多模态模型」各能正确提取几个地点、每篇成本多少。计价前查当前官方价格，不凭记忆。
2. **对照评测雏形**：同一批都灵帖子交给 ChatGPT 与小红书 AI，按 7.1 的指标记录，作为后续对比基线。

阶段 ① 明确不做：memory、天气调整、住宿推荐、慕尼黑与威尼斯走廊、图文卡片。

## 10. 参赛与合规

- 资格：用户已确认居住瑞士，有未来在当地注册公司和开展主要研发的意愿；完整资格以申请时的真实信息和官方条款为准。
- 叙事：住在瑞士的中文旅行者，把零散的小红书攻略变成有依据、走得通的公共交通行程。如实披露 TREK 底座、rednote_mcp 既有工作与本次新增功能；未完成的功能、未证明的优势、佣金渠道及市场需求均列为假设。
- 数据来源合规：产品路线以用户自己导入为主；原型阶段的自动抓取使用创始人本人账户，在演示中标注，不作为产品能力宣传。
- 许可：遵守 AGPLv3 第 13 条及分发要求；公开源码前剔除登录会话、个人旅行资料和密钥。

## 已作废的旧决策（2026-10-06 第一轮）

| 旧决策 | 新决策 |
| --- | --- |
| 目的地可留空，由系统推荐 | 用户选 1–3 个目的地 |
| 生成三个按体验侧重区分的完整方案 | 地点池取舍后生成一个方案，可切换侧重重新推荐 |
