# 瑞士假期旅行攻略助手：决策、动态行程与图文创作

> **最新实施依据：**用户已通过 grilling 确认改为“从瑞士出发旅行的中文用户”，本地自动采集、免费规划、预订佣金假设，验收为 Turin 四日游和因特拉肯周末游。见 [确认方案与实施计划](travel-prototype-implementation-plan.md)。本文保留早期设计，单次付费、中国赴瑞士首轮客群等旧提案不再作为当前决策。

> 2026-10-06｜创始人已确认主题并扩大定位：假期旅行决策 + 天气与交通动态行程 + 图文创作；覆盖周末、短假、长假及中国赴瑞士游客｜设计阶段，尚无用户访谈、使用或收入；以下功能未实现。

## 1. 当前主题

把用户看到、收藏的旅行灵感，变成符合个人偏好且交通可行的完整攻略，再生成可编辑、可分享的原创图文。

主题已经确定：将原方案 01 的决策能力扩展为假期旅行决策，以原方案 02 的天气与交通动态行程作为执行能力，再增加原创图文创作。三者共用偏好、地点证据与行程版本，构成同一个产品。周末是其中一种场景，产品名称、入口和数据模型不以周末为限制。

产品服务瑞士旅行的中文用户，包括瑞士及周边居民，也包括从中国来瑞士度假的游客。覆盖一天往返、短假和多城市长假；支持不同入境/离境地点，不要求苏黎世出发或当天返回。公共交通作为首轮重点，自驾完整路线支持另行规划。

首轮开发建议用三个样例贯通：一天往返、3 天短假、7 天多城市旅行。样例用于控制数据核验和演示规模，不代表产品只支持这些天数；任意日期范围的数据模型从一开始支持，实际生成能力应按验证情况说明。酒店不再是必要客户或分发渠道。原酒店及十方向文档保留为备选，旧申请稿尚未改成这个主题，不能直接用于新方向提交。

用户是旅行者，分享是旅行规划的延伸。旅行博主批量生产内容可以成为后续独立客群，但首版不同时承担两套需求。

### 1.0 两类用户的输入差异

| 用户 | 典型输入 | 规划重点 |
| --- | --- | --- |
| 瑞士及周边居民 | 住址或出发城市、假期日期、预算、兴趣、去过的地方 | 新鲜感、返回时间、短假节奏、重复推荐控制 |
| 中国赴瑞士游客 | 瑞士抵达与离开地点/当地时间、总天数、已订住宿、同行人、想去的地点 | 跨城市顺序、住宿衔接、行李移动、抵达日休息、离境余量、中文地名与交通说明 |

用户可手工输入航班抵达与离开时间作为固定约束；首版不承诺航班实时查询、签证办理或住宿预订。未订住宿时提供建议住宿城市与晚数，具体酒店可用性和价格保持待核验。

### 1.1 三个部分的首版验收

| 部分 | 用户问题 | 首版行为与验收 |
| --- | --- | --- |
| 假期旅行决策 | 假期去哪、去几处、怎样安排更适合我？ | 不要求先选具体城市；根据偏好、日期、起终点和预算给出 3 个可比较方案，说明城市顺序、住宿晚数、交通负担和天气适配 |
| 天气与交通动态行程 | 选好了，但下雨或交通变化怎么办？ | 为选定方案生成排程；用户主动刷新时重新查询可用数据，显示变化与备选，保留锁定项目，由用户确认应用 |
| 图文创作 | 怎么把攻略快速整理成小红书内容？ | 从当前确认的行程生成文案和 4–6 张卡片，支持预览、修改、下载；行程变更后提示重新生成 |

首版动态调整采用主动刷新，显示查询时间与覆盖范围。后台持续监控、即时推送和无人值守自动改行程列入后续阶段；不能把一次查询称作持续实时监控。

长假分成两层规划：先决定城市/住宿分布，再排每天活动与交通。远期天气超出数据源预报窗口时按季节资料和可替换活动规划，并明确不是实际天气预测；临近出行再核验。住宿、抵达和离境作为固定锚点，天气变化优先调整当天活动，跨城市及住宿变动须单独确认。

### 1.2 开发顺序

1. 先贯通偏好输入、三个候选方案、选择方案和保存行程，用少量人工核验路线作为初始内容。
2. 加入 OJP、天气查询、可行性检查和用户确认的变化调整。
3. 加入当前行程到图文模板的生成与导出。
4. 小红书内容采集并行做可行性验证，通过后接入候选内容层；无法读取时继续支持正文、截图和链接记录。

每一步交付可使用的完整流程。自动采集不是攻略生成必须成功的前置条件。

## 2. 一次完整使用流程

1. 输入假期日期、起终点、同行人、预算、交通方式与体力偏好；赴瑞士游客补充抵达/离境时间和已订住宿。目的地可留空，由系统推荐三个旅行方案并比较；已有路线时直接完善。
2. 粘贴感兴趣的小红书链接，或提供有权使用的笔记正文、截图。系统也可通过经过验证的内容采集适配器寻找候选笔记；失败时提供导入入口。
3. 提取景点、体验、地点、季节、停留时间和作者经验，合并重复地点。用户勾选必须去、可选和不想去的项目。
4. 结合可查询的交通、天气、营业信息，生成每天的顺序、时间、交通、预算区间和备选方案。
5. 用户修改“少走路”“加咖啡馆”“这个景点保留”等要求，系统保留锁定项目后重新计算；主动刷新天气与交通后，展示变化、影响和可接受的替代方案，确认后更新版本。
6. 导出攻略地图、文字清单，以及封面、路线、时间表、预算等 4–6 张图文卡片。用户预览、修改后自行发布。

示例输入：“周六从苏黎世出发去卢塞恩，两个人，公共交通，每人预算 CHF 100，喜欢湖景和拍照，不爬山，晚上八点前回来。这三篇笔记里的两个地点我想保留。”预算、交通覆盖与返回要求均应经过检查，不保证每个输入都有可行解。

长假样例：“从中国来瑞士玩 7 天，两人，苏黎世抵达、日内瓦离开，住宿只订了第一晚，喜欢湖景、雪山和小镇，每天不想换酒店。希望参考这几篇收藏安排路线。”先询问具体当地时间、预算是否包含国际机票及住宿等缺失约束，再生成城市/晚数分配与每日计划，不虚构酒店订单。

## 3. 最值得做的区别

热门内容用于发现地点和体验；热度不能证明内容正确或适合用户。系统应回答为什么选择或排除某个地点，例如“湖景符合偏好，但这两个地点当天衔接需要额外两小时，建议拆开”。

核心价值是把多篇笔记里的零散信息组合成可执行行程，并给出来源、核验日期和未确认事项。生成文章只是最后一步。不能在未验证竞争格局前声称这是独有技术。

## 4. 内容采集：先做技术验证

目前查到的小红书账号开放平台 API 目录包括授权、Token 和用户基本信息，没有列出通用热门笔记搜索接口。账号授权不等于获得内容抓取权限。这是所查文档的范围判断，并不证明不存在其他合作接口。

可用输入分为三类：用户提供的正文或截图；用户提供且能够按允许方式读取的链接；经过权限、用途及稳定性验证的搜索或内容来源。不要把未经确认的数据供应商能力写成已有集成。

搜索与采集适配器接口：`searchNotes(query, cursor)`、`importNote(input)`。返回来源链接、获取时间、发布日期、可用正文、地点候选及可观察到的互动数；字段缺失时标记未知。没有覆盖完整搜索结果时，只能称“本次检索候选”，不能称全平台热门榜。

第一周用少量真实样本验证分享链接解析、正文获取、动态页面、登录依赖、字段完整度和更新成本。遇到验证码或访问限制停止并走导入流程。浏览器采集依赖会话、页面结构和平台允许范围，不作为稳定公共 API 承诺；不收集用户账号密码。

全文临时处理、结构化事实留存与展示摘要分别设计。原帖图片不默认用于新帖子；保存来源与删除入口。正式规模化采集前核对平台条款、访问方式和内容使用许可。

## 5. 数据模型与生成链路

| 对象 | 主要字段与用途 |
| --- | --- |
| SourceNote | 来源 URL、发布时间、获取时间、摘要、可用性、使用范围 |
| PlaceCandidate | 标准地点、坐标、地点别名、体验标签、证据来源、待核验事项 |
| TravellerPreferences | 本次行程的任意起止日期、预算口径、起终点、当地抵达/离开时间、兴趣、体力、同行人、硬约束；默认值取自 TravellerProfile |
| TravellerProfile | 跨行程的长期画像：偏好条目、来源等级、依据、置信度、更新时间；用户可查看、修改、删除、导出，见 5.1 |
| PreferenceSignal | 方案选择/拒绝及原因、锁定/排除地点、行程修改、行后复盘；只追加，作为画像更新的依据 |
| StayAnchor | 住宿城市、日期/晚数、地址、是否已订、可否移动；未订酒店与确认订单分开 |
| TripOutline | 城市顺序、每城天数与住宿晚数、跨城交通、已确认锚点 |
| VerifiedFact | 事实值、核验来源、有效日期、状态；保留冲突而非直接覆盖 |
| ItineraryVersion | 每天活动与交通、锁定项目、预算范围、未解决事项、版本号 |
| ShareDraft | 基于哪个行程版本、分享类型、文案、图片、用户修改与导出状态 |

链路：采集/导入 → LLM 结构化抽取 → 地点消歧与去重 → 偏好召回排序 → 城市与住宿晚数分配 → 交通与事实核验 → 每日排程 → 行程说明 → 图文草稿。

把硬约束交给程序检查：时间重叠、交通连接、返回时限、营业时间、停留时间、预算口径与步行限制。信息未知时说明缺口，不能由模型补造。无解时明确解释并提出可选择的放宽条件。

首版采用规则过滤和排序即可，不需要训练推荐模型或复杂向量平台。地点按名称、地理距离与人工复核去重；以后有真实数据再评价语义检索价值。多轮修改只重算受影响日期，关联图文草稿标记过期。

### 5.1 长期旅行画像：越用越懂用户

> 2026-10-21｜用户提出参考开源项目 [career-ops](https://github.com/santifer/career-ops)｜设计阶段，未实现。

目标：第一次使用只靠简短问卷，随着规划和出行次数增加，助手积累对用户的了解，后续方案更贴合个人。参考 career-ops 的做法：它不训练模型，而是维护用户可读的档案（`cv.md`、`profile.yml`）、带结果状态的台账，以及只提建议、不自动改评分的校准模式。本产品照此设计，不宣称模型“自主学习”。

| career-ops | 本产品 |
| --- | --- |
| 个人档案 | TravellerProfile：硬约束（饮食禁忌、体力、预算区间、交通方式、同行人）与口味（自然/城市、餐饮风格、节奏、拥挤容忍度） |
| 申请台账与结果 | 行程记录：计划、实际去过的地点、行后评分与踩雷原因 |
| 面试故事库 | 个人地点库：去过的地点、喜欢或不喜欢及原因，用于去重与“去过的地方不重复推荐” |
| 权重注明来源，估计值不进最高档 | 偏好分三级：用户明确说明 > 多次行为体现 > 单次推断；推断项不得当作硬约束 |
| calibrate 只建议、不改评分 | 系统提出“你似乎不喜欢一天换两座城市，是否记录？”，用户确认后才写入画像 |
| 系统层与用户层分离 | 画像与记录归用户所有，可查看、修改、删除、导出，与规划逻辑分开存储 |
| 不编造简历事实 | 画像条目必须能追溯到问卷回答、PreferenceSignal 或用户编辑；不凭空生成偏好 |

**信号来源**：三方案中的选择与拒绝原因、锁定/排除地点、对行程的修改、补正的地点、行后复盘。行后复盘相当于 career-ops 的面试结果，是判断推荐是否有效的关键数据。

**冷启动**：5–8 个问题的简短问卷，加上可选导入 TREK 已有行程与收藏，形成粗略初始画像，并标注为低置信度。

**使用方式**：规划时把画像整理成摘要放入提示信息；每个方案注明“因为你的 X 偏好，所以选择/排除 Y”，并区分依据来自画像还是本次输入。画像摘要也可通过 TREK 内置 MCP 服务器提供给外部 AI 助手，以只读方式开放，权限另行设计。

**隐私**：画像属于敏感个人数据，只存本地或用户自己的部署；不得写入日志、演示材料或公开源码；删除画像时同时删除相关信号。

**分期**：信号事件从第一次生成方案就开始记录，因为过去的行为无法事后补记；画像整理、校准建议与 MCP 开放放在核心规划流程完成之后。

## 6. 与 TREK 的关系

复用行程、天数、地图、预算、交通接口和现有 LLM 调用基础；现有预订信息抽取逻辑不能直接当作旅游笔记抽取器，需要新的结构化输出和校验。

新增后端模块建议：`travel-sources`、`place-candidates`、`guide-planner`、`share-drafts`。内容读取适配器与行程业务隔离，便于切换导入、浏览器或其他许可来源。

交通模块继续保留 OJP 适配器计划，在后台查询瑞士公共交通，映射到现有统一行程结构。OJP 不是小红书内容获取接口，也不等于已有 SBB 私人账户集成。

首版保留现有登录流程，增加简化的偏好表单和导入页面。匿名使用、多人协作和多租户酒店后台不进入这轮范围。网络导入复用或补齐 SSRF 防护、大小限制、超时和任务重试；外部正文作为数据处理，不执行其中的指令。

## 7. 图文与发布

第一版用 HTML/SVG 模板渲染清晰、可编辑的竖版卡片：封面、每日路线、交通时间表、预算、注意事项。地图、用户自有照片或获许可素材优先；生成式插画可以作为装饰，不能假装是真实景点照片。

输出模式分成“计划攻略”和“旅行后游记”。尚未出行时写计划与资料整理，不能生成虚构的亲历体验。旅行后用户补充照片、实际花费与感受，再形成个人游记。

官方分享 SDK 文档说明已取消自动填充标题、文案、话题，媒体内容不受该项变化影响；接入还需登记和审核。首版承诺下载图片、复制文案和预览，官方分享能力列为接入验证项。已有小红书 MCP/Playwright 经验可用于评估后续流程，但未经实际测试、权限确认与用户发布确认，不承诺无人值守自动发帖。

## 8. 首版范围

必须完成：一种可稳定使用的输入方式、结构化地点抽取、偏好与硬约束、任意日期范围及住宿锚点的数据模型、短途与多城市行程生成、OJP 交通查询、来源与未知状态、图文导出。首轮用一天、3 天、7 天案例分别验收；更长行程的生成性能、核验成本和质量另行测量，不默认视为已经验证。

同时进行但不阻塞核心体验：自动检索和笔记读取的小规模可行性验证。若稳定性不足，明确调整为“收藏内容转攻略”，而非长期宣传自动抓全站热门帖子。

暂缓：全世界目的地、酒店预订、精准全票种最低价、自动批量发帖、博主代运营和社区信息流。

## 9. 六周计划与工作量

以下是一名熟悉项目的开发者的规划估计，未做完整实现拆分；每天约 6 小时有效开发。六周包含用户验证与内容核验，不能全部算作编码时间。

| 周 | 产出 | 验收重点 |
| --- | --- | --- |
| 1 | 内容获取验证、偏好表单原型、5 次目标用户访谈 | 至少一条稳定输入路径；用户提供真实规划案例 |
| 2 | 抽取、地点去重、来源视图、少量覆盖多个城市的候选内容 | 对人工标注样本检查地点与经验抽取错误 |
| 3 | OJP 适配、城市/住宿分配、每日排程与预算检查 | 一天、3 天和7 天样例能发现不可行连接及抵达/离境冲突 |
| 4 | 天气查询、行程编辑、锁定住宿、版本与备选建议 | 修改偏好不会丢失锚点或留下旧交通；远期天气明确标注未知 |
| 5 | 图文模板、导出、5–10 人试用与收费页面 | 下载文件清晰；内容和当前行程一致 |
| 6 | 修复、真实付费实验、演示和参赛材料 | 区分访谈、试用、付款；保留实际证据 |

原短途范围粗估为演示 7–12 个开发人日、试点 22–35 个开发人日，扩大为多城市假期后不能直接沿用。城市/住宿分配、固定锚点及跨日重排暂估追加 5–10 个开发人日，真实内容覆盖与核验另计；尚未做详细拆分。六周目标改为覆盖三个样例的可演示原型与小规模试用，稳定商业试点时间在拆分后重估。自动搜索/登录采集、官方分享审核等待及维护另计。若第一周访问能力不稳定，先交付导入路径。

## 10. 收费实验与指标

先测试单次付费，符合旅行低频需求。实验价格可以是 CHF 4.90 与 CHF 9.90/份可编辑完整攻略；免费提供简短预览，付费包含完整排程、备选与图文导出。价格是待验证假设，不代表已证明支付意愿。订阅等重复需求出现后再测试。

分别记录居民短途与赴瑞士多日游客的支付意愿和单位生成成本；旧短途价格只作为起始实验，长假收费需单独验证。长行程图文支持全程概览与分日卡片，不把每一天强塞进同一套 4–6 张图。

邀请目标用户带自己正在计划的真实旅行和已有收藏，比较手工规划、通用聊天工具与本产品。记录首次有效攻略耗时、重大交通/事实错误、修改次数、实际使用、付款与再次使用。分享导出率只是辅助指标，不能代替旅行价值。

后台按生成任务记录内容获取成功率、抽取错误、核验覆盖、模型及地图成本、重试次数和人工支持耗时。不把点赞量当作推荐质量的主要目标。

## 11. 参赛叙事与证据

问题：社交平台的旅行灵感分散，难以按个人约束拼成真正能走的路线。

产品：结合内容理解、偏好建模和公共交通核验，把灵感转成可编辑行程与原创分享材料。

技术优势待验证：来源可追踪、硬约束检查、修改后的行程一致性；独立创始人已具备生产 AI、LLM 编排及小红书工具经验，但过去项目不是本项目的用户或收入证据。

演示应展示同一批内容如何为不同体力、预算和同行人生成不同方案，以及如何拒绝一条交通不可行的热门路线。申请中如实写早期开发及尚无牵引力，之后用真实验证替换。个人旅游主题不自动符合 Work, Reimagined；若未来面向内容创作者工作流程，再单独评估 Spotlight。
