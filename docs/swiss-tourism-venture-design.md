# 瑞士本地旅游创业产品：方案设计文档

> 版本：v0.1｜日期：2026-10-06｜状态：产品方案草案，尚未开始实现
>
> 主方案：酒店数字礼宾 + 基于天气、交通与用户约束的动态行程建议。
>
> 本文以 TREK 为技术底座。主方案是根据当前讨论选出的建议方向，尚未经过用户访谈或付费验证。产品名称、地区、价格、规模和效果指标均为规划假设，不代表已经确定或达成。

十个方向的独立产品与技术设计、六周计划、收费实验及参赛准备，现已扩展为 [十方向方案集](swiss-tourism-options/README.md)。本文件继续保留酒店主方案的详细设计。

## 1. 项目概述

### 1.1 一句话定位

为瑞士住宿机构提供一个多语言旅行助手：住客扫码后，获得从酒店出发、符合时间与体力要求的当地行程；天气或交通变化时，获得可解释、可确认的替代建议。

### 1.2 价值主张

对游客：减少查找、比较和重新规划的工作，让有限的旅行时间更容易安排。

对酒店：把前台反复回答的当地游玩问题整理成可维护的服务，并了解哪些推荐被使用。

对当地体验商家：通过住宿入口接触需求匹配的游客；这部分价值需要合作和转化数据验证。

### 1.3 初期形态

- 浏览器优先，手机页面为主，提供 PWA 能力。
- 酒店通过二维码、入住邮件或前台链接分发。
- 游客无需注册即可体验；保存或跨设备使用时再提供可选账号或恢复链接。
- 初期只支持一个地区，维护一批人工核验的地点和路线。
- 收入先验证酒店订阅，后续再考虑体验分成和目的地机构合作。
- 基于 TREK 开源改造，使用独立品牌，并遵守 AGPL 与数据来源的许可要求。

### 1.4 为什么选择这个方向

普通旅行规划产品需要直接获客，使用频率和付费意愿均不确定。酒店方案同时提供明确的分发入口、潜在付费方和可以测量的业务效果。

这一判断仍是商业假设。若访谈发现酒店不愿分发、不愿维护内容或没有采购预算，应先缩小为人工礼宾试验，或转向其他方向，而不是持续扩大开发范围。

## 2. 瑞士场景与证据边界

### 2.1 已确认的外部条件

| 条件 | 对产品的意义 | 来源 |
| --- | --- | --- |
| 瑞士存在多种公共交通票券、通票与优惠产品 | 推荐需要考虑用户已有票券及适用范围 | [SBB 票券](https://www.sbb.ch/en/offers/all-tickets) |
| Swiss Travel Pass 包含部分交通与博物馆权益，山地铁路等项目的待遇存在区别 | 不能把所有交通与景点统一标为免费 | [瑞士旅游局说明](https://help.myswitzerland.com/hc/en-us/articles/213124709-Which-services-does-the-Swiss-Travel-Pass-include) |
| 部分目的地提供住宿 Guest Card，例如卢塞恩的当地公共交通权益 | 酒店位置与住宿权益可以影响方案 | [卢塞恩 Guest Card](https://meetings.myswitzerland.com/en-gb/inspiration/lucerne-2/) |
| 公共交通开放平台提供时刻表及实时数据产品 | 可以验证交通可行性与变化检测 | [瑞士交通开放平台](https://opentransportdata.swiss/en/) |
| MeteoSwiss 提供开放的当地预报数据 | 可以构建天气适配和变化检测 | [预报数据文档](https://opendatadocs.meteoswiss.ch/e-forecast-data/e4-local-forecast-data) |
| SwitzerlandMobility 已提供徒步、骑行等信息 | 需要通过场景与服务价值形成差异 | [SwitzerlandMobility](https://schweizmobil.ch/) |
| 路线封闭信息可能不完整，且需要出发前重新检查 | 路线状态需要明确来源和新鲜度 | [封闭与绕行说明](https://www.schweizmobil.ch/de/sperrungen-umleitungen) |

以上事实不能直接证明酒店愿意付费，也不能证明现有竞品没有相同功能。票券、供应商条款和赛事规则可能变化，上线或提交材料前需要重新核对。

### 2.2 必须通过访谈验证的假设

1. 酒店前台在推荐当地活动方面存在重复工作。
2. 酒店愿意将第三方页面提供给住客，并愿意支付服务费。
3. 游客愿意填写少量偏好，以换取更适合自己的建议。
4. 天气变化造成的行程调整是足够频繁、值得解决的问题。
5. 一个地区的内容维护成本可以被少量酒店订阅覆盖。
6. 酒店分发可以比直接面向游客投放广告更有效地获得用户。

### 2.3 市场估算方式

当前不填写未经核实的市场规模。后续分三层估算：

- 总体市场：目标地域内适合采购该服务的住宿机构数量 × 可验证年客单价。
- 可服务市场：语言、地区、内容覆盖与采购条件符合要求的机构。
- 初期可获取市场：团队能实际拜访和支持的机构，结合销售周期估算。

酒店入住量、二维码触达率、页面使用率和续费率需要分别测量，不能用全国旅游人次直接推导订阅收入。

## 3. 备选方向与选择依据

以下方向保留为产品拓展或主方案验证失败后的备选，不在首版同时实现。

| 方向 | 目标用户与问题 | 核心能力 | 可能收入 | 首期判断 |
| --- | --- | --- | --- | --- |
| 周末短途助手 | 本地居民不知道周末去哪 | 时间、预算、票券和偏好匹配 | 会员、渠道合作 | 复用程度高，但付费与留存待验证 |
| 动态行程助手 | 游客遇到天气或交通变化 | 约束重算、预订锁定、替代方案 | 旅程付费、酒店订阅 | 作为主方案核心能力 |
| 票券优化助手 | 不理解通票与优惠组合 | 覆盖规则、成本对比、组合计算 | 单次付费、合作收入 | 精确票价获取和维护门槛高 |
| 家庭旅行 | 推车、午睡、厕所等细节难规划 | 经核验的家庭属性与时间安排 | 会员、住宿合作 | 可作为首个细分客群 |
| 多代同行 | 带父母出行，体力和节奏不同 | 步行、换乘、休息与海拔偏好 | 旅程付费、机构合作 | 可作为第二个细分客群 |
| 酒店数字礼宾 | 前台反复推荐，游客资料分散 | 酒店内容、扫码入口、多语言建议 | 酒店订阅 | 推荐的商业入口 |
| 商务短时旅行 | 会议结束后时间有限 | 机场返回、行李寄存、时间约束 | 会议与商务酒店采购 | 适合后续渠道实验 |
| 无车户外路线 | 起终点交通与返程难协调 | 路线与公共交通衔接 | 会员、目的地合作 | 需投入路线可靠性维护 |
| 游客分流工具 | 热门地点集中，其他体验难曝光 | 容量、兴趣和条件匹配 | 目的地机构采购 | 合作与数据周期较长 |
| 多人出游协调 | 时间、预算和出发地难统一 | 共同可行解、投票、分摊 | 团队服务、会员 | 可复用 TREK 协作能力，付费方待定 |

选择主方案时优先考虑：能否接触真实用户、谁支付、能否小范围试验、数据能否维护，以及是否能在截止日前形成可信证据。表中的判断来自当前分析，不是完成竞品研究后的结论。

## 4. 客户、用户与试点地区

### 4.1 角色划分

| 角色 | 目标 | 主要权限 |
| --- | --- | --- |
| 游客 | 获取并调整自己的行程 | 编辑自己的偏好和行程，查看公开酒店内容 |
| 前台员工 | 快速提供建议，处理游客求助 | 管理本酒店内容；经游客授权查看其行程 |
| 酒店管理员 | 配置品牌、员工、路线与订阅 | 管理本酒店配置及聚合使用数据 |
| 内容编辑 | 核验地区信息 | 编辑授权地区内容，不能读取游客私有数据 |
| 平台运营者 | 管理酒店、来源、故障与服务 | 受审计的运维权限 |
| 体验商家 | 提供体验信息和链接 | 后续阶段开放限定内容提交权限 |

### 4.2 第一批客户假设

优先访谈独立酒店、精品酒店和小型酒店集团。其采购决策可能较短，但具体预算与使用习惯需要验证。

大型连锁酒店、滑雪度假区和旅游局留作后续：它们可能有更多集成、品牌和采购要求。

### 4.3 地区选择

卢塞恩及周边可以作为候选，因其住宿、城市活动、湖区和山地活动可形成多种方案。它尚未被正式选定。

如果团队在其他地区更容易接触酒店，应优先选择有渠道的地区。实际选择按以下条件打分：

1. 至少能接触两三家愿意参与访谈的住宿机构。
2. 团队能现场核验路线和交通衔接。
3. 同一区域内有室内、城市、自然等替代活动。
4. 地点来源和商业使用条件清楚。
5. 内容维护范围可控制。

### 4.4 初期语言

建议先做英语和当地主要语言，候选卢塞恩对应德语。若试点酒店明确有中文需求，再增加中文。

现有 TREK 翻译能力可以复用，但新文案、地点说明和运营内容仍需要翻译与核验。支持多语言界面不等于内容已经有多语言版本。

## 5. 用户流程与页面设计

### 5.1 游客流程

1. 扫描酒店二维码，进入酒店欢迎页。
2. 选择出行日期、可用时间、同行人数、步行偏好和已有票券。
3. 查看两三套行程建议，比较时间、费用估算、体力与天气适配。
4. 选择一个方案并保存，获得地图、交通段和地点卡片。
5. 查看最新状态；系统提示某项活动可能受到变化影响。
6. 比较替代方案与原计划，确认后更新自己的行程。
7. 对推荐是否有用提供反馈，必要时向酒店请求帮助。

首次推荐最多保留少量必填问题。日期、酒店出发点和本地时区可以预填，预算、票券与兴趣允许跳过。

### 5.2 酒店流程

1. 平台开通酒店并邀请管理员。
2. 酒店核对地址、联系方式、内容、当地权益和推荐路线。
3. 设置公开二维码与欢迎文案。
4. 前台分发入口，并记录使用中的问题。
5. 管理员查看聚合数据和待核验内容。
6. 试点结束时复盘，决定是否付费继续。

### 5.3 页面清单

| 页面 | 必须呈现的信息 | 关键操作 |
| --- | --- | --- |
| 酒店欢迎页 | 酒店身份、服务用途、语言、联系入口 | 开始规划 |
| 偏好表单 | 时间、同行人、步行与交通偏好 | 生成建议 |
| 推荐比较页 | 方案摘要、估算费用、交通、适配原因 | 选择方案 |
| 行程页 | 时间线、地图、活动与交通状态、更新时间 | 调整、收藏、离线保存 |
| 变化建议页 | 原因、受影响项目、替代方案、费用变化 | 确认、拒绝、稍后处理 |
| 酒店内容后台 | 地点、模板、有效期和来源 | 编辑、审核、撤下 |
| 酒店统计页 | 触达、使用、反馈及样本量 | 导出聚合报告 |

### 5.4 示例情境

住客住在候选试点酒店，希望上午九点出发、下午五点返回；两名成人，一名儿童，不开车，连续步行不超过三十分钟。

系统从核验模板中给出：城市与博物馆、湖边轻松游、条件允许时的观景活动。每套方案标明交通来源、天气适配和估算费用。

若观景活动对应的天气条件变差，系统提出室内替代，保留住客锁定的午餐预约。只有住客确认，才生成新的行程版本。示例不代表具体地点当前可营业或票券实际覆盖。

## 6. MVP 范围与验收条件

### 6.1 首版范围

| 功能 | 首版实现 | 验收条件 |
| --- | --- | --- |
| 酒店入口 | 独立欢迎页、品牌、地址和二维码 | 不同酒店内容不串用 |
| 游客私有会话 | 无需注册，保存个人偏好与行程 | 扫同一个公共码不会看到其他人的行程 |
| 地区内容 | 约 30–50 个核验地点、10–20 套模板 | 推荐字段有来源、更新时间及状态 |
| 偏好匹配 | 日期、时间、步行量、同行人和交通偏好 | 不满足硬约束的方案不进入候选 |
| 推荐 | 模板加规则，输出两三套方案 | 显示适配原因；无结果时说明原因 |
| 交通 | 接入或复用交通供应商，验证关键衔接 | 区分计划时刻、实时状态与未知状态 |
| 天气 | 预报与活动适配提示 | 历史天气不会被当作未来预报 |
| 变化建议 | 天气优先，交通变化按数据可得性加入 | 受影响项目、替代差异清晰可见 |
| 确认与版本 | 修改前比较，确认后生成版本 | 重复请求不会产生重复版本 |
| 离线 | 已保存行程与内容快照 | 显示快照时间和在线核验入口 |
| 内容后台 | 酒店内容、模板与核验管理 | 普通员工只能编辑授权范围 |
| 反馈与统计 | 推荐反馈、聚合漏斗与前台记录 | 数据不包含公开可识别的个人行程 |

地点与模板数量是试点容量目标，具体数量以内容质量与可维护性为准。

### 6.2 暂缓功能

- 全国覆盖与开放式无限行程生成。
- 完整实时票价最优解、自动购票和自动退款。
- 自动修改酒店、餐厅或景点预订。
- 酒店 PMS 深度集成。
- 全量商家市场、自建支付与结算体系。
- 高风险山地活动、滑雪或登山的安全决策。
- 社交社区、跨酒店画像和复杂多人协调。

### 6.3 首版完成定义

从一家酒店入口开始，游客可以完成偏好输入、选择可解释方案、保存行程、收到一次可验证的条件变化建议、确认或拒绝，并提供反馈。酒店能维护内容、看见聚合使用数据。上述流程必须在手机上完成，并覆盖数据失败和无候选结果的情况。

## 7. 推荐与动态调整逻辑

### 7.1 推荐流程

1. 从已发布且未过期的地点和模板中选候选。
2. 用硬约束过滤。
3. 根据兴趣、舒适度、天气适配、交通简便程度和预算偏好排序。
4. 验证入选方案的关键营业时间与交通衔接。
5. 生成两三套差异明显的选项及解释。

初期使用模板和可解释规则。若某些关键字段未知，应降低置信度或排除需要该字段的活动，而不能用 AI 补出一个事实。

### 7.2 硬约束与软偏好

| 类型 | 示例 | 处理方式 |
| --- | --- | --- |
| 硬约束 | 最晚返回时间、明确步行上限、已知关闭、锁定预约 | 违反则拒绝方案 |
| 软偏好 | 喜欢湖景、少换乘、偏好低花费 | 用于排序，显示权衡 |
| 未知信息 | 设施状态、未验证优惠、实时交通缺失 | 明示未知，必要时排除或请求确认 |

用户可区分“必须满足”与“尽量满足”。费用数据不完整时，不应把预算上限承诺为已满足。

### 7.3 初始排序示例

作为试点可调参数，可用兴趣 25%、舒适度 25%、天气适配 20%、交通便利 20%、预算适配 10% 形成排序。权重是示例，不是训练或研究结果。

酒店推荐与付费推广单独标记。付费推广不应突破硬约束或伪装成自然排序。

### 7.4 变化检测

状态划分为：正常、需要核验、建议调整、已知不可用、数据不足。

可能触发建议的事件：

- 活动对应的预报指标进入其不适合范围。
- 已接入的交通数据出现影响关键换乘或返回时间的变化。
- 酒店或内容编辑确认活动临时关闭。
- 用户主动更改时间、步行偏好或同行需求。

天气阈值由活动类别与来源核验定义，初期采用保守、可解释规则。普通天气预报不能替代山地风险评估。系统也不能因为没有收到封闭信息就宣称路线安全。

### 7.5 更新策略

- 用户打开行程时，刷新关键状态。
- 对近期、活跃行程按供应商限额定期检查；建议先测试 30–60 分钟间隔。
- 酒店确认的关闭信息立即影响新推荐与相关建议。
- 夜间及非活跃行程减少轮询，避免成本失控。
- 首版主要使用页面内提醒；邮件或 Web Push 后续按用户授权接入。

### 7.6 变更确认

替代方案必须显示保留项目、替换项目、时间和费用估算差异、未知项，以及是否触及外部预订。

首版只变更本产品中的行程安排，外部购票与预约通过链接完成。确认不代表供应商预订已改变，界面必须清楚区分这两种状态。

### 7.7 AI 的职责

AI 可用于理解用户自然语言偏好、解释规则结果、翻译已核验内容和生成摘要。首版规则推荐可以不依赖 AI，以降低成本并便于调试。

AI 不负责创造营业时间、票价、优惠覆盖或路线安全结论。事实必须绑定来源；文本中的关键数字应由结构化字段渲染，并在输出后校验。

## 8. 数据与外部服务设计

### 8.1 数据源矩阵

| 数据 | 当前代码或候选来源 | 用法与限制 |
| --- | --- | --- |
| 地点与地图 | TREK 地图能力、许可允许的地点来源、酒店核验 | 核对图片、文本和地图署名；公开可见不等于可复制商用 |
| 基础天气 | TREK 当前使用 Open-Meteo | 核对商业使用条件、限额与预报范围 |
| 瑞士当地预报 | MeteoSwiss Open Data | 核对参数、时效、下载形式与使用条件 |
| 交通规划 | TREK 默认 Transitous，可选现有其他供应商 | 对试点路线做覆盖验证，不默认其信息完整 |
| 瑞士时刻表与实时状态 | opentransportdata.swiss | 按选定产品配置 API、覆盖、限额和缓存 |
| 票价接口候选 | OJP Fare | 官方已列出票价服务；验证访问、覆盖与限额，报价不等同购买时最终价格 |
| 票价与权益 | 运营商官方规则、酒店与当地机构 | 首版人工维护规则与估算；未获得接口前不承诺实时最优价格 |
| 营业与关闭 | 运营方、酒店、内容编辑 | 保存来源、核验时间和有效期 |
| 步行及设施属性 | 公开可靠来源与现场核验 | 属性缺失保留未知，尤其是无障碍与儿童条件 |

MeteoSwiss 的数据接入可能需要文件下载与参数处理，不能假设所有开放数据都有简单的地点查询 API。首版先做小规模数据适配验证。

补充核对：瑞士交通开放平台列出了 [OJP Fare](https://api-manager.opentransportdata.swiss/portal/catalogue-products/tedp_ojpfare-1)。其 [官方说明](https://opentransportdata.swiss/en/cookbook/open-journey-planner-ojp-landing-page/)指出报价不具约束力且查询受限；接口存在不代表已经取得访问权限或覆盖所有票券。酒店首版仍以核验权益与明确标注的估算为主。

### 8.2 数据状态

每条关键事实记录：来源类型、来源链接、观察或获取时间、人工核验时间、有效期、状态和适用范围。

内容工作流：草稿 → 待核验 → 已发布 → 待复核／过期 → 撤下。过期的关键事实不能继续被视为可靠推荐依据。

### 8.3 费用展示

费用拆分为交通、活动和其他预计支出，并显示人数、币种、用户票券假设、估算日期与不包含项目。

价格不完整时显示区间或“待确认”。不使用未经确认的 Guest Card 权益推导零费用，不将过期优惠继续纳入计算。

### 8.4 故障降级

- 天气失败：展示最近快照及时间，暂停基于过期天气的自动调整。
- 实时交通失败：可以展示可靠的计划时刻，并明确实时状态不可用。
- 关键营业信息未知：提供替代或要求游客核验，避免确定性承诺。
- AI 失败：继续使用模板和结构化说明。
- 全部候选不满足约束：展示无法满足的具体条件，允许用户自行放宽偏好。

### 9.3 初期部署方案

推荐首期采用“每家酒店一个独立运行实例、独立数据库及存储目录”的试点模式，以减少在庞大现有系统上立即改造所有数据访问的风险。

- 一家酒店对应一个逻辑隔离的应用实例，部署自动化可共享代码与镜像。
- SQLite 作为单实例初期数据库，备份、上传、缓存及配置分别隔离。
- 酒店内部继续隔离不同游客的私有行程。
- 平台可用部署清单管理试点酒店；首版不强制开发复杂中央控制台。

缺点是实例数量增长后运营成本增加，内容同步需版本化。若试点证明需要规模化，再评估共享数据库或独立数据库的租户架构；不得仅添加 `hotel_id` 就认为隔离完成。

### 9.4 后续共享租户演进

若进入共享应用模式，必须系统覆盖数据库查询、上传和照片代理、分享令牌、WebSocket 房间、缓存、离线存储、定时任务、备份恢复、API、MCP 和插件权限。

酒店租户与行程成员权限是两个层次。默认限制非必要插件、MCP 和公开管理接口，逐项完成隔离验证后再开放。

### 10.1 核心对象

| 对象 | 关键字段 | 说明 |

| HotelStaff | 用户、酒店角色、内容权限 | 从已有登录用户扩展 |

| LocalExperience | 地点、时长、设施、活动类别、来源状态 | 核验内容 |
| RouteTemplate | 活动序列、适用条件、交通约束、内容版本 | 推荐候选基础 |
| BenefitRule | 票券或权益类型、范围、有效期、来源 | 不等同于已验证的持券资格 |

### 10.2 行程归属问题

现有 TREK 行程依赖用户和成员权限。实现前需要完成一个技术验证：匿名游客是否使用受限的临时内部主体，或通过独立 GuestPlan 服务访问专用行程数据。

建议先验证“临时主体 + 默认拒绝的访客守卫”是否可行：该主体不通过普通登录接口访问，不进入酒店员工目录，所有操作再检查私有会话与行程归属。若无法在现有全局权限中可靠隔离，应改用专用访客数据层。

绝不能让全部游客使用一个共用用户并直接访问通用行程接口。

### 10.3 接口示例

以下均为拟新增接口，尚未存在：

| 接口 | 用途 | 权限 |
| --- | --- | --- |
| `GET /api/concierge/hotel` | 酒店公开资料 | 公开、限流 |
| `POST /api/concierge/sessions` | 创建私有访客会话 | 公开、限流 |
| `PUT /api/concierge/preferences` | 保存本人偏好 | 私有会话 |
| `POST /api/concierge/recommendations` | 生成候选 | 私有会话、额度限制 |
| `POST /api/concierge/plans` | 选定并保存方案 | 私有会话 |
| `GET /api/concierge/plans/:id` | 查看本人行程 | 会话归属校验 |
| `GET /api/concierge/plans/:id/proposals` | 获取变化建议 | 会话归属校验 |

访客身份通过安全 Cookie 或其他经过设计的会话机制承载，不能依赖可枚举的行程编号。公开二维码是分发入口，不能本身赋予读取所有访客数据的权限。

### 10.4 版本一致性

接受建议时提交 `expected_version` 和幂等键；服务端检查建议未过期、条件仍有效、行程版本一致，再在事务中写入新版本。

离线确认只排队保存“确认意图”，不能显示为已完成；联网后重新核验。旧建议失效时要求重新比较，重复请求返回同一次确认结果。

## 11. 隐私、权限与运行要求

### 11.1 数据最小化

首版不需要身份证、护照、房间号、健康诊断或精确实时位置。体力需求尽量使用“步行上限”等功能偏好，不要求游客描述疾病。

前台默认只看到聚合数据。游客请求帮助时可主动授权分享自己的行程，并能撤销。

### 11.2 保存与删除

候选政策：游客可以随时删除会话，匿名行程在最后活跃后 30 天删除；试点分析事件保留 90 天，再进行不可识别聚合或删除。期限需要结合业务与适用规则最终确认，当前不是法律结论。

不要将邮件、完整行程或恢复令牌写入普通分析事件。不得为追求统计而把不同酒店的访客身份合并。

### 11.3 会话与链接

- 私有令牌应具有足够随机性，支持到期与撤销。
- 酒店公共入口不承载游客个人信息。
- 私有链接避免出现在第三方分析或引用头中。
- Cookie 模式需要 CSRF、防滥用和来源验证设计。
- 外部 AI 只接收必要字段，不发送身份资料与预订确认号。

### 11.4 服务运行

正式试点使用 HTTPS，支持 WebSocket 代理和 PWA 的实际浏览器条件。配置持久化数据库、上传目录、备份与恢复演练。

监控关注推荐失败、供应商错误、数据过期、确认冲突、内容缺失及每次推荐成本。首版采用单节点持久化架构，避免把 SQLite 放到多个无协调写入实例上。

初期建议推荐响应 95 分位低于 10 秒，关键页面可在供应商故障时打开已保存快照。这些是设计目标，需要试点测量。

## 12. 商业模式与单位经济

### 12.1 收费实验

| 阶段 | 收费方式 | 假设价格与条件 |
| --- | --- | --- |
| 访谈／人工服务 | 不收费或约定试用 | 换取真实使用与复盘，不换取虚假好评 |
| 基础酒店订阅 | 每酒店每月 | 可测试 CHF 99–199，限定地区与额度 |
| 增强服务 | 订阅加内容支持 | 可测试 CHF 299–499，提供更多内容维护或品牌配置 |
| 定制上线 | 单次服务费 | 根据实际工时报价，避免把定制成本隐藏在订阅中 |

这些价格是访谈用的测试区间，尚未经过市场研究。不要直接写进参赛材料作为已证实收入模型。

### 12.2 可选后续收入

- 体验商家的可披露转化分成。
- 酒店集团或目的地机构采购。
- 游客个人高级功能。

首版不依赖佣金成立，因为结算、归因、合作和游客信任都需要额外工作。

### 12.3 成本结构

直接成本包括实例托管、地图／交通／AI 调用、内容维护、客服支持和支付成本。销售、研发与管理成本另外记录，不能在毛利中忽略后就认为公司盈利。

主要核算单位：每酒店每月成本、每活跃游客成本、每成功推荐成本，以及每家酒店每月内容与支持工时。

### 12.4 示例测算

假设一家酒店月费 CHF 149，当月托管与调用成本 CHF 25，内容及支持成本 CHF 50，则直接贡献 CHF 74，贡献率约 49.7%。这只是算式示例，不代表实际成本。

若想达到 60% 的直接贡献率，同一价格下直接成本需要控制在 CHF 59.60 以内。初期即使未达到，也应知道差距来自内容、支持还是技术调用，不能笼统归因于规模不足。

### 12.5 开源与竞争优势

计划把修改后的服务按 AGPL 提供对应源码，通过托管、部署、可靠内容和持续服务收费。不开源酒店私有资料、游客数据或凭证。

竞争优势假设是渠道关系、核验内容维护能力、真实场景中的约束处理和运营效率。仅有开源代码修改、AI 提示词或更多界面，不足以证明长期优势。

## 13. 验证计划与决策门槛

### 13.1 第一阶段：问题访谈

建议访谈 8–12 家酒店相关人员、15–20 位游客、3–5 家当地体验运营者。优先询问过去的真实经历：

- 前台最近一周最常回答什么游玩问题？
- 最近一次天气变化，游客如何改计划？
- 现在用什么资料和软件？谁负责更新？
- 酒店如何采购这类服务，谁有预算和决策权？
- 游客为什么没有采用某项推荐？

避免只问“你觉得这个产品好吗”。尽量获取试用约定、分发方式和可测量问题。

### 13.2 第二阶段：人工礼宾试验

在完整开发前，用简单页面和人工推荐服务测试输入表单、推荐质量、前台分发及付费讨论。

建议规模为 2–3 家酒店、30–50 名真实游客。若实际触达不足，先解决渠道；不要根据少量扫描数据判断算法无效。

### 13.3 第三阶段：MVP 试点

按一地区、少量酒店运行 2–4 周。记录邀请或展示入口、扫码、完成偏好、选定方案、查看详情、反馈及实际采用情况。

页面点击只能证明兴趣，不能当作实际旅行或商家收入。实际采用可以通过自愿反馈、前台记录或经授权的合作记录验证，并标明其测量限制。

### 13.4 指标定义

| 指标 | 分子／分母 | 用途 |
| --- | --- | --- |
| 入口触达后的使用率 | 唯一扫码访客／可记录的受邀或触达访客 | 判断分发效果；无法测触达时不报告该率 |
| 表单完成率 | 完成偏好的会话／开始填写的会话 | 判断输入负担 |
| 方案选定率 | 保存方案的会话／成功看到推荐的会话 | 判断推荐吸引力 |
| 建议接受率 | 确认有效建议数／已展示有效建议数 | 判断动态调整价值 |
| 推荐满意度 | 正面反馈数／有效反馈数 | 同时报告反馈率与样本量 |
| 前台节省时间 | 基线与试点同类咨询用时差异 | 判断酒店价值；控制入住量与员工差异 |
| 付费转化 | 真实付费酒店／完成试点且收到报价的酒店 | 判断采购意愿 |
| 直接贡献 | 实收订阅减去对应直接成本 | 判断服务经济性 |

### 13.5 初始继续／调整标准

建议以至少 3 家完成试点的酒店、累计 50 个有效推荐会话作为第一轮复盘样本目标。小样本只用于方向判断，不做全国市场推断。

可设置初始目标：表单完成率至少 60%，方案选定率至少 35%，至少 2 家酒店愿意按明确报价进入付费或签署有条件试用延续。后者应区分口头意愿、意向书和真实付款。

- 若没有分发：调整入口与酒店流程。
- 若有流量但推荐不被选：检查内容、需求匹配和输入质量。
- 若游客喜欢但酒店不支付：验证其他付费方或服务包装。
- 若内容维护无法被收入覆盖：减少覆盖或调整价格。
- 若数据长期无法可靠获取：收敛为核验模板产品。

所有门槛均是初始实验参数，不能当作行业标准或已达到结果。

## 14. 实施路线与资源

### 14.1 六周参考路线

以下计划假设有一名熟悉 TypeScript 的全栈开发者，以及一名能承担酒店访谈和内容核验的协作者。投入不足时需要缩减功能与酒店数量。

| 周次 | 工作 | 可审查产出 | 依赖 |
| --- | --- | --- | --- |
| 第 1 周 | 资格确认、访谈、地区选择、数据接入小验证 | 访谈记录、试点承诺、数据可行性报告 | 渠道与参赛资格 |
| 第 2 周 | 人工礼宾试验、内容结构、欢迎页与表单 | 核验模板、用户反馈、交互原型 | 地区与酒店 |
| 第 3 周 | 实例隔离、访客会话、行程保存 | 手机端完整基础流程、权限验证 | 访客身份方案 |
| 第 4 周 | 推荐规则、天气适配、交通核验 | 两三方案比较、失败降级 | 数据与内容质量 |
| 第 5 周 | 建议、版本确认、后台和统计 | 可运行 MVP、运维说明 | 基础流程稳定 |
| 第 6 周 | 试点、修正、效果与成本复盘 | 使用报告、演示、申请材料 | 酒店实际分发 |

测试可以先采用可控天气与交通样本演示逻辑；必须明确标识模拟数据，并另外验证真实数据接入。不可把模拟演示当作真实商业效果。

### 14.2 第一批开发任务

1. 记录现有数据库、权限和分享链路，验证匿名主体接入。
2. 为一家酒店配置独立实例、HTTPS、备份及恢复。
3. 创建酒店欢迎页和私有访客会话。
4. 定义核验地点、模板、来源状态的共享协议。
5. 实现模板筛选与可解释推荐。
6. 接入并核验试点天气、交通数据。
7. 实现变更建议、版本校验与幂等确认。
8. 接入聚合事件与反馈。

任务 5 依赖内容和协议；任务 7 依赖稳定的行程归属与状态模型。不能并行绕过这些依赖。

### 14.3 验证重点

测试关注真实业务风险：会话越权、酒店实例边界、过期数据、交通返回约束、锁定预约、并发确认、离线重放、语言与时区，以及无可用方案。

内容类修改以人工核验为主；无需为每段文案编写镜像测试。新增 API、权限与版本逻辑应有必要的集成测试，手机核心流程应有端到端验证。

### 14.4 运营交付

试点上线时交付二维码、酒店使用说明、内容核验清单、游客反馈入口、故障联系渠道、成本记录与退出流程。技术上线不等于试点完成，必须确认酒店实际向住客分发。

## 16. 许可与知识产权

TREK 的代码许可为 AGPLv3。修改版本通过网络提供服务时，应向相关用户提供对应源码；分发时还需遵守相应许可义务。没有按改动比例自动免除义务的规则。[AGPL 官方文本](https://www.gnu.org/licenses/agpl-3.0.html)

实施要求：

1. 保留必要版权、许可和修改说明。
2. 在服务中提供清晰的源码获取入口，并对应实际部署版本。
3. 不把用户私有数据、密码、API 密钥或运行凭证包含在源码包中。
4. 实质改造的产品使用独立名称与标识，遵守仓库 `TRADEMARKS.md`。
5. 按 `NOTICE.md` 和实际使用资源保留数据、图片与地图署名。
6. 不假设插件、独立仓库或 API 分离就自动允许闭源；涉及独立性和特殊授权时另行审查。

若后续商业策略要求闭源，应选择独立开发或取得必要的其他授权。当前方案不以获得商业授权为前提。

## 17. 风险与应对

| 风险 | 早期信号 | 应对与决策 |
| --- | --- | --- |
| 酒店需求不强 | 不愿分发或讨论采购 | 先做人工服务，收缩开发投入 |
| 游客不使用 | 扫码少、表单放弃高 | 改入口、减少问题、突出具体价值 |
| 推荐价值低 | 选定率低、经常人工推翻 | 缩小客群和地区，增加核验 |
| 数据不可靠 | 频繁过期、时间或费用错误 | 限定来源、显示未知、提供替代 |
| 内容维护过重 | 每酒店支持工时持续增长 | 模板复用、明确额度、调整收费 |
| 现有产品已经解决问题 | 酒店展示等价服务且满意 | 深入比较，调整差异或停止方向 |
| 品牌与许可处理不当 | 去掉许可、混用 TREK 品牌 | 独立品牌、源码发布和署名流程 |
| 游客数据越权 | 公共链接可访问他人行程 | 私有会话、归属检查、必要集成测试 |
| 天气建议被误解 | 用户把推荐当成安全保证 | 明确适用范围，限制高风险活动 |
| 瑞士资格不满足 | 没有有效创始人或公司关联 | 先核对资格，不虚构关联 |

## 18. 下一步与待决策事项

当前建议顺序是：资格核对 → 酒店访谈 → 数据与身份接入验证 → 人工礼宾试验 → MVP → 付费与效果复盘。

开始开发前需要决定：

1. 哪位创始人或公司满足赛事的瑞士关联要求？
2. 哪个地区最容易获得酒店与内容核验支持？
3. 第一类游客是普通住客、亲子家庭还是多代同行？
4. 谁负责每周内容维护与酒店支持？
5. 实际投入的人力与试点预算是多少？
6. 团队是否接受 AGPL 衍生版本的源码提供要求？

这些答案不妨碍先开展访谈与可行性验证，但会影响产品范围、部署方案和参赛材料。
